# HansBug 文章类型骨架

本文件给出 HansBug 中文技术博客常见文章类型的写作骨架。骨架不是死模板，而是为了让 agent 在构思时先抓住文章的推进方向：从哪里切入、用什么判断坐标、怎样收束。

## 技术实践文

### 适用场景

用于记录工具配置、工程链路、自动化方案、环境搭建、部署排障、脚本改造等实践问题。

### 推荐结构

1. 缘起：最近被什么问题追着打，为什么值得写。
2. 问题定义：本文解决什么，不解决什么，涉及哪些版本或环境。
3. 先说结论：最终采用的方案是什么。
4. 为什么旧做法不够：解释旧方案短板，不要只说“不好”。
5. 我的方案：步骤、配置、代码、验证方式。
6. 坑点与边界：哪些情况会失败，怎么排查。
7. 总结：把一次配置上升到工程维护判断。

### 禁区

- 只贴命令不解释取舍。
- 把“能跑”当作“设计成立”。
- 不说明适用环境和失败边界。
- 用官方文档重新排版冒充实践经验。

## 教程 / 学习笔记文

### 适用场景

用于解释某个工具、语言特性、论文工具链、写作环境或学习路线。

### 推荐结构

1. 写在前面：为什么现在写，读者应如何使用本文。
2. 整体定位：这个东西解决哪一类问题，不是什么。
3. 概念拆分：把容易混在一起的术语先拆开。
4. 实操方案：给出可执行路径。
5. 关键细节解释：解释为什么这些步骤必要。
6. 常见坑：列出最容易踩的坑和排查方式。
7. 一点总结：给出长期维护建议。

### 禁区

- 把教程写成百科词条。
- 不交代版本、平台或前置条件。
- 只告诉读者怎么做，不解释为什么这样做。
- 为了“完整”而塞入和主线无关的资料。

## 复盘 / 事故分析文

### 适用场景

用于分析失败、冲突、排障、流程问题、项目事故、课程或协作中的结构性问题。

### 推荐结构

1. 事故缘起：发生了什么，影响了谁。
2. 先给结论：根因或核心判断是什么。
3. 表面现象：读者最容易看到的症状。
4. 根因分析：把现象背后的设计、流程或认知错误拆开。
5. 为什么难查：说明误导点、盲区和假线索。
6. 反思与改法：给出能落地的修复方向。
7. 总结：上升到制度、方法或长期维护判断。

### 禁区

- 写成流水账。
- 只追责不分析结构。
- 把情绪当洞察。
- 没有复现路径、影响范围或后续改法。

## 测评 / 评论文

### 适用场景

用于评价产品、工具、课程、项目、平台或某套设计方案。

### 推荐结构

1. 评测范围与标准：先说明用什么坐标评价。
2. 总体判断：先给结论，不要拖到最后。
3. 分维度体验：功能、交互、性能、可维护性、用户成本。
4. 问题与影响：哪些问题不是小瑕疵，而会伤到用户或维护者。
5. 建议：给出可改方向，不能只开喷。
6. 更高层总结：把产品体验上升到设计思路或组织问题。

### 禁区

- 先入为主地开喷。
- 表扬很空，批评也很空。
- 不说明评价标准。
- 只站在单一角色视角看问题。

## 课程 / 项目总结文

### 适用场景

用于总结课程作业、助教工作、团队项目、开源项目、阶段性经历或长期协作。

### 推荐结构

1. 完整过程回顾：交代阶段，不要直接堆成果。
2. 各阶段判断：每个阶段发生了什么、暴露了什么问题。
3. 个人总结：作者从中学到了什么，哪些看法被改变。
4. 更深一层反思：制度、协作、工程方法或价值判断。
5. 鸣谢或补充说明：可以有，但不能替代判断收束。

### 禁区

- 只写“做了什么”，没有“为什么重要”。
- 把总结写成履历展示。
- 不区分个人经验和普遍结论。
- 没有最终判断，只剩礼貌收尾。

## 选型建议

当一篇文章同时像多种类型时，优先选择主问题最强的类型：

- 主问题是“怎么把它搞定”：技术实践文。
- 主问题是“怎么理解并上手”：教程 / 学习笔记。
- 主问题是“为什么会坏”：复盘 / 事故分析。
- 主问题是“这个东西到底怎么样”：测评 / 评论。
- 主问题是“这段经历说明了什么”：课程 / 项目总结。

不要为了显得全面把所有骨架揉在一起。骨架可以混用，但主线只能有一条。

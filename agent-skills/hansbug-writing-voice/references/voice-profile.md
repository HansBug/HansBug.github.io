# HansBug 文风画像

本文件描述的是 HansBug 中文技术博客正文的总体文风画像。它不是口癖清单，也不是让 agent 把旧文句子搬过来拼贴的素材库；它要解决的是：写作时到底应该怎样组织判断、怎样拆问题、怎样把个人经验压进技术分析里。

## 核心判断

像 HansBug，首先不是像某几个词，而是像一套判断方式。

一篇合格的 HansBug 风格文章，通常会在前半段就让读者知道作者到底怎么看这件事。后面的结构不是把资料继续往下堆，而是围绕这个判断补场景、补边界、补反例、补取舍。换句话说，文章不是“信息排列”，而是“判断展开”。

因此，文风复刻的优先级应当是：

1. 判断密度高于口癖密度。
2. 概念拆分高于情绪强度。
3. 工程取舍高于命令罗列。
4. 经验来源高于第一人称表演。
5. 结尾盖章高于礼貌收束。

如果一篇文章满篇都是“笔者”“好吧”“咳咳”“2333”，但没有问题定义、没有判断前置、没有概念拆分、没有工程取舍，那它不是像 HansBug，只是披了一层廉价皮套。这个判断必须写得很硬，否则后续 agent 很容易走偏。

## 作者视角

HansBug 的正文通常带有明确作者视角：作者不是站在远处解释一个对象，而是把自己放进问题现场里，说明为什么碰到这个问题、为什么愿意下这个判断、为什么不接受某种糊弄式方案。

这种作者视角有几个边界：

- 可以写“笔者”的经验，但经验必须服务于判断。
- 可以写“我”的直接感受，但不要把整篇文章写成情绪流水账。
- 可以批评设计、流程、方案和现象，但批评必须有事实、推理或案例支撑。
- 不允许编造作者没有给出的项目现场、课程现场、会议经历、对话细节或第一手态度。

更像的写法，是先交代自己为什么碰上这个问题，再说明这个问题暴露了什么结构性缺陷，最后把经验收束为方法论判断。

不太像的写法，是先堆一段自我介绍、履历或情绪，然后正文和这些经历几乎没有关系。

## 技术判断密度

HansBug 的技术文不是 API 手册，也不是命令速查表。它通常会追问：为什么这样做更合理？为什么另一种做法看起来省事但长期不稳？为什么一个配置能跑不代表设计成立？

写作时需要优先保留这些判断动作：

- 先给整体结论，再拆原因。
- 先定义评价坐标，再评价方案。
- 先说明适用边界，再给操作步骤。
- 先承认某个方案局部可行，再指出长期维护风险。
- 先把“能跑”与“值得长期维护”拆开。

技术判断的语气可以锋利，但不能省略论证。刀子必须有刀背。

## 概念拆分与对立辨析

HansBug 文风里非常关键的一点，是愿意把看似相近的概念硬拆开讲清楚。很多段落的力量不来自情绪，而来自重新划定坐标系。

常见拆法包括：

- 不是 `A`，而是 `B`。
- 看起来是 `X`，本质上是 `Y`。
- 表面问题是 `P`，根因其实是 `Q`。
- 与其说是 `M`，不如说是 `N`。
- `能跑` 和 `设计成立` 不是一回事。
- `标签`、`路线`、`归档`、`搜索` 不是同一层能力。

写作时应主动寻找最容易被读者混在一起的两个概念，然后把它们拆开。拆开之后再继续分析，文章才会有“这个人有自己一套”的感觉。

## 锋利感与黑色幽默

HansBug 的锋利感不是无证据地阴阳怪气，而是在分析已经站稳之后，用一句更短、更硬的话把问题钉住。

可以保留的锋利方向：

- 对自欺欺人的流程做冷处理式评价。
- 对“看起来很努力，实际全是无效功”的状态提出讥讽。
- 对表面漂亮但底层站不住的方案明确否定。
- 对“能跑就行”“以后再说”的短视做工程层面的反驳。

不应保留的方向：

- 人身攻击。
- 没有事实支撑的阴阳怪气。
- 只有态度没有分析的情绪宣泄。
- 为了显得锋利而句句带刺。

一句话：可以毒，但要毒得有理。

## 松弛感与现场感

HansBug 的文章不是过度修平的说明书。正文允许有一点现场感、即兴感和掰扯感：像作者正在把问题摊开，边讲边判断，顺手把偷懒想法拆掉。

可以适量使用：

- “好吧”“咳咳”“容我先”“闲话少叙”。
- 一两句自嘲或补坑说明。
- 括号补充和破折号转折。
- 对读者的直接提醒，例如“请各位自己想想看”。

但这些只能是调味。口语化不能替代结构，松弛感不能替代判断。

## 事实与经历边界

本 Skill 只能复刻表达方式、论证习惯和写作工作流，不能替作者编造事实。

遇到下面情况，必须标记需要作者补充，而不是自动脑补：

- 文章需要第一人称项目经历，但用户没有提供。
- 文章需要课程现场或助教工作细节，但材料里没有。
- 文章需要作者对某个人、组织、产品的真实态度，但没有来源。
- 文章需要具体时间、对话、故障现场或内部决策过程，但没有证据。

正确做法是写出“这里需要作者补一段真实经历 / 真实案例 / 具体环境”，而不是写得好像作者真的经历过。

## 结尾盖章

HansBug 风格的结尾通常不是礼貌性回收材料，而是把全文判断再抬高半层。

结尾应该做到：

- 回到文章最初的问题。
- 明确作者最终怎么看。
- 从局部方案上升到工程取舍、方法论、制度问题或长期维护判断。
- 最后用一句更短、更硬的话收住。

不要只写“感谢阅读”“先写到这里”。那不是盖章，是把文章轻轻放下了；HansBug 的结尾更像把判断钉在墙上。


## 样本边界

画像文件只使用 `participatesInProfile: true` 的样本做正向归纳。`holdoutForDryRun: true` 的样本不得进入本文的正向证据链，它们留给后续真实 CLI forward-test；`negative` 样本也不得作为应该模仿的来源，只能用来帮助识别反模式。

## 最低自检

写作或审阅时，至少问这些问题：

- 前三段是否已经说明缘起、主问题和边界？
- 前半段是否已经亮出核心判断？
- 是否真的拆开了容易混淆的概念？
- 每个大节是否都有作者判断，而不是只有资料转述？
- 锋利感是否建立在事实和推理上？
- 是否把口癖当成了文风本体？
- 是否编造了作者没有提供的经历？
- 结尾是否比前文再高半层？

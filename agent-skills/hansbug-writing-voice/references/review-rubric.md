# HansBug 文风审稿 Rubric

本文件给 HansBug 中文博客正文提供可执行的审稿坐标。它不是给 agent 发“像一点”的玄学命令，而是把“哪里必须挡住、哪里必须返工、哪里只是润色”拆成 C/I/M 三档。审稿时可以语气锋利，但结论必须能落到证据、位置和修复动作上。

## 使用边界

- 只审 `src/content/blog/` 下中文博客正文或准备进入正文的草稿。
- 不审首页、按钮、导航、项目短介绍等页面文案。
- 不替作者编造经历、项目现场、课程现场、会议对话或第一手态度。
- 不把本 rubric 当成版权豁免；旧博客样本只允许作为结构、语气和判断方式参考，不允许整段搬运。
- 机械 gate 只能挡住明显偏离；最终“像不像”仍需要人或 reviewer 结合全文判断。

## 总体评分坐标

审稿时先看骨架，再看皮肤。优先级如下：

1. 核心判断是否靠前、明确、可辩护。
2. 问题边界是否清楚，读者是否知道本文解决什么、不解决什么。
3. 概念拆分是否真实存在，而不是顺着常见话术滑过去。
4. 工程取舍、长期维护和失败方式是否被说明。
5. 作者经验是否有来源，是否服务于判断。
6. 松弛、锋利、口癖、黑色幽默是否只是调味，而不是主菜。

一句话：高口癖密度 + 低判断密度是假模仿，不是 HansBug 文风。

## C 级：必须阻断

出现 C 级问题时，不能让文章以“文风已达标”的名义继续过关。PR review 里必须明确列出证据和修复方向。

### 缺少核心判断

识别信号：全文只有“介绍”“总结”“值得注意”，但看不出作者赞成什么、反对什么、为什么这样判断。

修复方向：在前三段补主问题、边界和核心判断；后文围绕判断展开，而不是继续堆资料。

### AI 式正确废话

识别信号：每句话都安全、平整、正确，但换一个作者名字也成立；“总体而言”“可以看出”“具有重要意义”频繁出现，却没有作者现场和工程取舍。

修复方向：删掉空泛总结，补具体问题链路、失败方式、判断坐标和可操作改法。

### 编造作者经历

识别信号：用户没有提供材料，文中却出现“我在某项目里”“我们开会时”“当时课程现场”“我曾经负责”之类第一手叙述。

修复方向：改成“这里需要作者补真实经历 / 真实环境 / 具体案例”，或改写为非第一手、可验证的公开事实。Skill 只能复刻表达方式，不能替作者制造人生。

### 无边界感

识别信号：技术文不说明版本、环境、适用场景、失败条件；把一次经验写成普遍真理。

修复方向：补“本文解决什么 / 不解决什么”、前置条件、失败方式和不适用场景。边界不是免责声明，而是判断的一部分。

### 高口癖密度 + 低判断密度

识别信号：“笔者”“好吧”“咳咳”“2333”很多，但没有问题定义、概念拆分、工程取舍和结尾盖章。

修复方向：先删口癖，重建判断主线。等骨架站住后，再恢复少量松弛表达。

### 使用 holdout / negative 样本做正向证据

识别信号：把 `sampleRole: negative` 或 `holdoutForDryRun: true` 的样本写成“应学习的正向文风来源”。

修复方向：只使用 `participatesInProfile: true` 的样本做正向对照；negative 只能做反例，holdout 留给 forward-test。

## I 级：重要返工

I 级问题不一定单独阻断发布，但如果一篇文章集中出现多个 I，应视为整体未 ready。

### 宏观结构松散

识别信号：有二级标题，但章节只是并列堆料；看不出从现象到本质、从实现到取舍、从经历到方法论的推进。

修复方向：重新安排章节功能，让每一节都服务于核心判断。

### 结尾没有盖章

识别信号：最后只写“感谢阅读”“先写到这里”“以上就是全部内容”。

修复方向：回到开头问题，把判断再抬高半层，用一句更硬的话收住。

### 概念拆分不足

识别信号：文章使用“好用”“稳定”“效率高”之类词，但没有拆开评价标准。

修复方向：补“不是 A，而是 B”“看起来是 X，本质是 Y”这类真实辨析，并说明为什么这个拆分影响结论。

### 资料搬运腔

识别信号：大段复述官方资料，作者只是串联信息。

修复方向：删掉和主问题无关的资料，只保留支撑判断的部分，并补作者自己的坐标系。

## M 级：轻微建议

M 级不阻塞，但能让文章更像本人。

- 个别段落太工整，可以增加一点长短句摆幅。
- 某个标题只写“背景”“方案”，可以改成带判断的标题。
- 某处锋利句略软，可以在事实后补一句落锤。
- 读者引导不足，可以补一句“如果只关心配置，先看这一节”。
- 个别口癖略多，可以删到只剩必要调味。

## 事实 / 经历来源评分轴

这一轴单独看，因为它是最容易被 AI 写坏、也最不能糊弄的部分。

| 等级 | 判定 | 处理 |
|---|---|---|
| C | 编造作者没有提供的第一手项目、课程、会议、对话、内部决策。 | 阻断；改为占位请求或删除。 |
| I | 经验存在但来源不清，无法判断是作者经历、公开事实还是推测。 | 要求补来源、补上下文或降格为推测。 |
| M | 来源基本清楚，但和核心判断连接弱。 | 建议压缩经历，补它为什么支撑判断。 |
| Pass | 经验来源清楚，且能自然导向方法论或工程取舍。 | 保留。 |

审稿时不要被“写得像真的”骗过去。越像第一手现场，越需要来源站得住。

## 审稿输出格式

建议每次审稿按下面格式输出：

```text
身份：<codex reviewer / claude reviewer / deepseek reviewer / 主 session>
结论：C=<数量> / I=<数量> / M=<数量>

C 级问题：
- [code] 位置 / 证据：...
  修复建议：...

I 级问题：
- [code] 位置 / 证据：...
  修复建议：...

M 级建议：
- [code] 位置 / 证据：...
  修复建议：...
```

如果没有 C/I，也要明确写“未发现阻塞项”。不要只说“整体不错”，那对后续迭代没有价值。

## 与机械 gate 的关系

`check_hansbug_voice.py` 只做粗筛：AI 腔、口癖堆砌、宏观结构缺口、样本引用边界、无来源经历、reference 摘录合规等。它的 `score` 不是文风相似度，只是粗筛健康度。脚本通过，不代表文章一定像；脚本失败，则必须先处理 C 级 finding。

# HansBug 宏观论述逻辑

本文件描述 HansBug 风格文章的宏观推进方式。它解决的是“文章应该怎样往前走”的问题，而不是某一句话应该怎么写。

## 总体轨道

最常见的推进轨道是：

1. 缘起 / 题外话破题。
2. 问题定义 / 边界交代。
3. 核心判断前置。
4. 分维度展开分析。
5. 补坑点、反例、例外或更深层原因。
6. 总结与上升一层的反思。

关键不在于必须写六节，而在于文章始终有一条判断主线。读者应该能看出作者从现象走向本质，从局部实现走向工程取舍，从一次经历走向方法论判断。

## 从现象到本质

HansBug 风格不会满足于描述“发生了什么”。它通常会继续追问：这个现象背后的本质问题是什么？为什么它不是小问题？如果不改会怎样？

推荐推进：

1. 先承认读者看见的表层现象。
2. 再指出这个现象为什么容易误导。
3. 然后把根因拆到设计、流程、认知或维护链路上。
4. 最后给出可操作的改法或明确方向。

## 从实现到工程取舍

技术实践文不能停在“命令能跑”。它要解释为什么这个实现选择在长期维护上站得住，或者为什么看似省事的方案其实是在给未来挖坑。

推荐推进：

1. 给出可运行方案。
2. 解释方案背后的约束。
3. 对比被放弃的方案。
4. 说明长期维护成本。
5. 明确边界和失败方式。

判断句可以硬一点：能跑只是最低门槛，不是设计成立的证据。

## 从经历到方法论

如果文章包含作者经历，经历不能只是履历展示。它应当承担“为什么作者有资格下这个判断”的作用。

推荐推进：

1. 交代自己为什么碰到这个问题。
2. 说明踩过什么坑或见过什么现象。
3. 把经历压缩成判断。
4. 再把判断上升到方法、制度或价值取舍。

如果缺少真实经历材料，必须向作者要材料，不能编造现场。

## 分维度拆解

中段分析不能只是并列堆料。每个维度都应该有明确功能：证明核心判断、解释边界、拆掉反例或给出改法。

可用维度包括：

- 用户视角。
- 开发者视角。
- 维护者视角。
- PM / 组织流程视角。
- 长期演化视角。

多视角不是为了显得全面，而是为了说明同一个问题会怎样伤到不同角色。

## 反例与边界

HansBug 风格通常会处理“真正难的地方”。这部分经常出现在倒数第二节，用来说明：方案在哪里不适用，哪些问题还没解决，哪些看似反例其实不构成反驳。

推荐写法：

1. 先承认局部例外。
2. 再说明例外为什么不推翻主判断。
3. 如果确实会推翻，就收窄适用边界。
4. 给出后续处理方向。

不要把边界写成免责声明。边界是判断的一部分。

## 结尾上升

结尾应当完成一次视角抬升：从本文的具体问题回到更长期、更稳定的判断。

可以上升到：

- 工程维护习惯。
- 协作流程设计。
- 产品设计思路。
- 学习和写作方法。
- 对糊弄式方案的明确否定。

结尾不需要很长，但要有落锤感。文章最后几句应该像盖章，而不是像客服结束语。

## 宏观自检

审阅时按这组问题检查：

- 文章主线是否只有一条？
- 前三段是否已经进入问题定义？
- 核心判断是否足够靠前？
- 每个大节是否推进了判断，而不是只补资料？
- 是否有处理例外、反例或边界？
- 结尾是否比前文再高半层？

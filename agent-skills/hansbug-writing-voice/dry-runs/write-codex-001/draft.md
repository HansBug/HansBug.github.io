在维护博客仓库这件事上，最容易被忽略的往往不是脚本本身，而是脚本失败之后那条路写没写清楚。命令报错不可怕，退出码非零也不可怕；真正麻烦的是它只丢出一坨日志，然后把下一个维护者、下一个 agent、下一个半夜想发文章的人，全都扔进同一片雾里。

先说结论：本地开发脚本的最低目标不是“永远成功”，而是“失败时能把人带到下一步”。尤其是面向个人技术博客仓库的维护脚本，它服务的不是某个宏大的线上业务容灾系统，而是构建、检查、迁移、生成索引、校验内容这些日常动作。这里的问题很小，但小问题如果没有出口，就会在协作链路里反复长刺。

## 先把边界钉住：这里谈的是仓库维护脚本

本文只讨论本地仓库维护脚本，例如构建前检查、内容 schema 校验、旧博客索引生成、图片资源整理、引用文件检查、部署前 dry-run 之类的脚本。不讨论线上业务容灾，不讨论多活架构，不讨论服务级熔断，也不讨论把个人博客仓库包装成一套大型平台工程。

这个边界必须提前说清楚。因为仓库维护脚本的失败路径，重点不是自动恢复一切，而是让维护者知道：失败发生在哪一步、它大概意味着什么、应该先看哪个文件、能不能安全重跑、如果不能重跑需要停在哪里等人处理。

换句话说，这里要解决的不是“系统怎样在故障里继续提供服务”，而是“脚本怎样在失败后不继续装死”。前者是可靠性工程，后者是维护纪律。两者不是一回事。

## 坑点：只写成功路径，其实是在把失败外包给读者

很多本地脚本写起来都很顺手：读取文件，跑一轮转换，打印 done，结束。看起来干净，甚至有点优雅。问题是，这种优雅经常只覆盖了成功路径，一旦输入缺字段、路径不存在、依赖没装、远端数据为空、生成物格式变了，脚本就开始用 Python traceback、Node stack trace 或一行含糊的 error 把人劝退。

说白了，这不是“脚本失败”，这是“脚本失败之后不交代后事”。它把本来应该由脚本作者提前写明的判断，全部甩给执行者现场猜。执行者如果是熟悉仓库的人，还能顺着代码摸一摸；如果是新来的协作者或本地 agent，那就只能在日志里考古。看起来省了十分钟，实际是在未来每一次失败时收利息。

比较靠谱的写法，至少应该把几类信息写出来：当前检查的对象是什么；失败条件是什么；这类失败能否自动修；不能自动修时应该改哪个文件；重跑前是否需要清理生成物；如果脚本依赖外部输入，输入为空和请求失败要不要区分。别的不说，把“下一步该做什么”写清楚，就已经比单纯抛异常强很多。

这里还有一个容易混掉的概念：详细日志不等于清晰失败路径。日志可以很多，但如果没有判断，它只是把噪声排版得更整齐；失败路径可以很短，但只要它告诉读者该停、该改、该重跑，维护成本就会立刻降下来。能打印一屏，不代表把问题讲明白了。

## 可以怎么写：让脚本在失败时给出可执行指令

对这类仓库脚本来说，一个实用的失败输出大致可以按四层写：失败摘要、失败原因、建议动作、风险边界。

失败摘要负责告诉人“哪一步坏了”。失败原因负责说明“为什么这不是正常结果”。建议动作要尽量落到具体路径、命令或检查项，例如 `src/content.config.ts`、`src/data/tagMeta.ts`、`npm run build`。风险边界则要说明“这一步能不能自动重试”“是否可能覆盖生成物”“是否需要先让作者确认”。

这套东西不需要写得很重。维护脚本不是论文，不必每个分支都写成长篇解释。但至少要避免那种只有 `failed`、`invalid input`、`unknown error` 的糊弄输出。脚本都已经知道自己在哪一步失败了，却不肯告诉读者下一步去哪，这就很难说是工程简洁，更像是把懒惰伪装成克制。

更进一步，失败路径最好和仓库约定绑定起来。比如新标签缺 metadata，就直接指向 `src/data/tagMeta.ts`；博客 frontmatter 缺字段，就指向内容 schema；旧博客索引生成失败，就说明数据源、生成目标和是否可重跑。这样脚本才不是一个孤立命令，而是仓库维护规约的一部分。

## 总结：失败路径是脚本的维护界面

本地开发脚本当然不可能覆盖所有异常，也没必要把个人博客仓库写成重型平台。但它至少应该做到一点：失败时不要让读者从零开始猜。

归根结底，脚本的成功路径是给机器看的，失败路径才是给维护者看的。一个脚本能跑，只说明它在理想输入下完成了动作；它失败时还能把人带回正确位置，才说明它真的进入了仓库的维护体系。

所以这事别想得太轻。失败不可怕，没有失败路径才可怕。

文章类型：技术实践文

主问题：一个临时脚本已经能跑，为什么还要把它改造成仓库内可维护工具？真正要讨论的不是“脚本能不能完成当前任务”，而是它在长期维护里会不会变成后续 agent 和作者都不敢碰、碰了就踩坑的隐形债务。

不解决：不讨论某一种脚本语言的完整工程化教程；不讨论大型 CLI 框架选型；不把个人博客仓库包装成复杂平台；不编造作者在哪个真实项目里因为脚本翻车的经历。

核心判断：临时脚本的最低目标是把一次事情办完，仓库内工具的最低目标是让下一次维护者能判断、能复现、能失败得明白。能跑只是底线，不是设计成立。一个脚本只要进入仓库维护链路，就不再是作者手边的“顺手小玩具”，而是会影响内容发布、数据生成、构建检查和后续协作的工程入口。

读者应该先看：维护个人站点、技术博客、数据索引、内容迁移脚本，且已经开始让 agent 或自动化工具参与维护的人。尤其是那些手上有一堆 `scripts/tmp_xxx.py`、`fix_once.ts`、`convert_old_data.js`，但每次重跑之前都要先在脑子里考古半天的人。

建议结构：

1. 缘起 / 破题：从“临时脚本最可怕的地方不是丑，而是它后来被人当成正式入口继续用”切入。可以用抽象场景写：个人技术博客里有维护脚本负责生成索引、清洗旧数据、检查内容字段或同步元信息。这里必须声明没有作者真实踩坑材料，所以只基于仓库维护场景做构思。

2. 问题定义 / 边界：拆开“脚本能跑”和“工具可维护”这两个概念。前者关心一次执行，后者关心入口、参数、错误提示、幂等性、文档、测试、目录位置、输出文件边界和后续 agent 是否能读懂。本文边界放在个人博客仓库内维护脚本，不上升到企业级平台治理。

3. 核心判断前置：把判断压到前面讲清楚：凡是会被重复执行、会修改仓库文件、会影响发布链路、会被 agent 调用的脚本，都应该按仓库内工具处理。反过来，一次性探索脚本可以保留粗糙，但不能悄悄混进正式维护路径。这个判断要带一点硬度：别把“当时省了十分钟”变成“以后每次都要烧半小时香”。

4. 分维度分析：  
   第一维是入口：命令名、参数、默认行为、dry-run、help 文案。维护工具应该让人不读源码也能知道它要干什么。  
   第二维是状态：输入从哪里来，输出写到哪里，是否会覆盖文件，失败后仓库会不会半脏不脏。  
   第三维是错误：不要只抛一坨栈，要告诉维护者错在哪个文件、哪个字段、下一步怎么修。  
   第四维是验证：至少有 smoke test 或 fixture，让后续 agent 改完之后能证明没有把发布链路炸穿。  
   第五维是归属：脚本放在什么目录、README 或 `package.json` / npm scripts 里如何暴露、哪些输出文件不该手改。

5. 反例 / 坑点：承认不是所有脚本都值得工程化。真正的边界是使用频率、破坏半径和知识沉淀价值。只跑一次、无副作用、不会进入发布链路的探索脚本，可以留在临时区甚至删掉；但只要它开始生成正式数据、修正文档结构、参与构建检查，就不能再靠作者记忆续命。还要特别写 agent 场景：未来 agent 不知道你当时脑子里那几条隐含规则，它只会读仓库里留下来的入口、注释、测试和错误信息。

6. 总结盖章：把文章收束到工程维护判断：把临时脚本改造成仓库内工具，本质不是追求“漂亮”，而是把隐性经验从作者脑子里搬回仓库。个人项目也需要这种克制，因为个人项目最容易把“只有我知道”误判成“以后我也会记得”。说白了，工具化不是给脚本穿西装，而是让下一次维护少一点玄学。

最近笔者又被自己半年前写的一个仓库维护脚本反咬了一口。脚本失败本身不复杂，无非是某个外部资源 404 了；真正让笔者烦躁的是，脚本失败之后，控制台只剩一句轻飘飘的 `Error`，既没说它走到了哪一步，也没说接下来应该怎么救场。修这点东西花的时间，比写这个脚本本身还长。

闲话先收一收。本文真正想钉住的判断只有一句：脚本失败不可怕，失败后没有清晰路径才可怕。下面这些段落，都是围绕这句话在拆。

## 适用边界先说清楚

这篇只谈一件事：仓库维护脚本。也就是那种平时躺在 `scripts/` 目录里、偶尔被人手动跑一次、出问题大不了重跑一次的小工具。本文 **不** 讨论线上业务容灾、不讨论 SLA、不讨论高可用，也不讨论 on-call 流程。这两类东西的失败成本完全不在一个量级上，把业务容灾那一套搬过来要求维护脚本，是另一种偷懒——它让人误以为“写得够重就够稳”。

笔者只关心维护脚本里最朴素的一种诉求：人能不能在两分钟之内看懂它为什么炸了，并且知道下一步该敲哪条命令。

## 真正的痛点不是“失败”，是“失败之后无路可走”

很多脚本写起来都有一种心照不宣的偷懒方式：成功路径写得明明白白，失败路径全靠抛异常。表面上看也没什么问题，反正 Python 会自动打 traceback。

但是请各位想想看，traceback 真的回答了下面这些问题吗：

- 脚本失败时，整体已经做完了哪一步？哪些副作用已经发生、哪些还没发生？
- 是不是已经写了一半文件、改了一半状态、动了一半远端？
- 是应该重跑、应该回滚、还是应该手动接管剩下的步骤？
- 如果是网络抖动那一类临时问题，下次重试有没有自动幂等的把握？

traceback 只回答“在哪一行炸的”。剩下这些问题，全靠下一个倒霉蛋自己猜。说白了，失败信息只覆盖了“失败本身”，没有覆盖“失败之后”。

笔者后来给自己定了一个底线：一个维护脚本如果不能告诉使用者“现在站在路径的哪个节点、下一步该往哪走”，那它就不算写完，只能算跑通。

## 笔者会强制让脚本暴露的几样东西

具体来说，每个维护脚本至少要把下面这几件事钉死：

1. **每一步必须有可见的起止信号。** 不是只打 `done`，而是要让使用者一眼看出脚本走到了哪一节。命名上笔者倾向于 `step 2/5: refresh catalog`，简单、扛得住时间。
2. **失败时必须明确给一句“下一步建议”。** 哪怕只是 `请检查网络后重试同一条命令`，也比让人对着空 traceback 发呆强得多。这句建议不需要写得多花哨，但必须存在。
3. **可重入性要写在脚本里、不要写在脑子里。** 哪些步骤幂等、哪些不幂等、不幂等的部分用什么标记位防止重复执行，这些都要在代码里说人话，而不是寄希望于读者自己推断。
4. **临时状态要落盘到一个可见位置。** 一旦中断，下次重跑能从哪里捡起来——这件事不能只靠注释暗示。

这几条不是为了让脚本显得“工程化”。它们要解决的全是同一个问题：让失败这条路径，也变成一条 **能被人接住** 的路径。

## 几个看起来无害、其实很坑的写法

笔者在自己和别人的脚本里反复见过这几种写法，看起来都很省事，长期看全是债：

- **只用裸 `raise` 不补任何上下文。** 写的时候觉得“反正异常会冒泡上去”，半年后再看就会感谢自己一顿。
- **把所有错误都 `except Exception` 吃掉。** 看似让脚本更鲁棒，实际上等于把所有失败路径压成同一种状态，无法区分“网络抖了”和“仓库被改坏了”。
- **失败时悄悄继续往后跑。** 这是最难追的一种。前面的步骤其实已经废了，后面的步骤却还在认认真真生成产物，最后产出物完全是错的，但脚本退出码是 0。
- **错误信息只对作者本人有意义。** 例如 `bad state at phase 2`。半年后连作者自己都看不懂 phase 2 是什么。

这些写法的共同特征是：写的时候图当下几秒钟的轻松，读的时候要付出几小时的代价。维护脚本的读者，绝大多数时候就是未来的自己；和未来的自己作对，这事不太划算。

## 总结：失败要能被接住，脚本才算写完

归根结底，维护脚本的稳定性，从来不是“它不会失败”，而是“它失败的时候，使用者能在没有作者陪同的情况下，自己走完接下来的路”。所谓“把失败路径写清楚”，本质就是把一段“只有作者知道怎么继续”的流程，改造成一段“任何接手的人都能继续”的流程。

把成功路径写漂亮，是脚本的下限；把失败路径写清楚，才是脚本的上限。维护脚本这种东西，决定它长寿与否的，从来不是它跑顺的那一天，而是它第一次炸在别人手里的那一天。

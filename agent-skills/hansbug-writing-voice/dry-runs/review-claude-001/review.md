### C 级问题（必须阻断，不能以"文风已达标"过关）

- **[C-缺少核心判断]** 位置 / 证据：全文三节（"背景 / 使用方式 / 总结"）从头到尾没有作者立场。
  - "这个工具可以帮助用户完成配置"——没说为什么需要它，没说它替代了什么糟糕做法。
  - "整体上比较方便，也具有一定参考价值"——"方便""有参考价值"是空话，看不出作者赞成什么、反对什么。
  - "综上所述，这个工具是有意义的"——结论等于没结论，把作者从文章里彻底删除。
  - 修复建议：前三段必须补主问题（这个工具到底解决了哪个具体痛点？没它会怎样？）、边界（适用范围、不适用场景）、核心判断（作者到底推不推荐、在什么前提下推荐、不推荐什么替代品）。后文围绕这个判断展开，而不是继续堆"使用步骤"。

- **[C-AI 式正确废话]** 位置 / 证据：短短三段里命中四个 AI 腔关键句式——"整体上比较方便""总体而言""综上所述""可以不断优化"。按 rubric 的机械 gate 口径，短文中密集出现这类词直接判 C 级，因为它们把作者判断稀释到零。
  - 修复建议：把所有"总体 / 综上 / 整体 / 有意义 / 提升效率 / 不断优化"删干净，逐句改写成带具体对象的判断。例如"这个工具是有意义的"必须替换成"它能省下 X 步手工配置；代价是 Y；如果你的场景没有 Y 的约束，那就值得用"这种带条件的判断。

- **[C-无边界感]** 位置 / 证据：通篇没有版本号、没有操作系统、没有前置条件、没有失败模式、没有不适用场景。"首先安装依赖，然后运行命令，最后查看输出"是一句把所有 CLI 工具都能套上去的话。
  - 修复建议：补"本文解决什么 / 不解决什么"、依赖的版本约束、典型失败链路（装不上怎么办？跑起来但输出是空的怎么办？）和明确的"如果你在 X 场景，不要用这个"。边界是判断的一部分，不是免责声明。

### I 级问题（重要返工，集中出现即整体未 ready）

- **[I-宏观结构松散]** 位置 / 证据："背景 / 使用方式 / 总结"三节是典型的并列堆料，看不到任何"从现象到本质 / 从实现到取舍 / 从经历到方法论"的推进。每一节内部也只是平铺信息。
  - 修复建议：按 rubric 推荐的"技术实践文骨架"重排——`缘起 → 先说结论 → 为什么旧做法不够 → 我的方案 → 坑点与边界 → 总结`。光把"使用方式"扩成一节是没用的，要让每一节都服务于核心判断。

- **[I-结尾没有盖章]** 位置 / 证据："综上所述，这个工具是有意义的，后续可以不断优化"——这是 rubric 里点名的反面教材"先写到这里 / 以上就是全部内容"的等价物。
  - 修复建议：结尾必须回到开头那个主问题，把判断再抬高半层。例如从"这个工具好用"上升到"这类自动化方案在长期维护上到底站不站得住，关键是要看 X 而不是 Y"——用一句更硬的话收住。

- **[I-概念拆分不足]** 位置 / 证据：用了"方便""效率""有意义""有参考价值"这种典型评价模糊词，但没有任何拆开评价标准的动作。整篇没有出现一次"不是 A，而是 B / 看起来是 X，本质是 Y"这种 HansBug 招牌辨析。
  - 修复建议：至少拆一次。例如"它不是省事，而是把易错环节从人脑挪到了脚本里"，或"它看起来在做自动化，本质上是在做配置约定的固化"。

- **[I-资料搬运腔（潜在）]** 位置 / 证据：当前稿子过短，资料搬运还没真正发生，但"使用方式"一节"装依赖、跑命令、看输出"的三步法已经是搬运腔的种子——如果扩写时继续往里塞官方文档片段而不补取舍判断，会迅速恶化成全段搬运。
  - 修复建议：扩写时只保留"为什么这一步是关键""这一步如果偷懒会出什么问题"这种和判断挂钩的信息，把纯命令贴出去就够了，不要逐行解释官方文档已经说过的话。

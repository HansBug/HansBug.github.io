C 级问题：

- `[ai-cliche-generic-summary]` 文风问题  
  位置 / 证据：候选稿多处使用空泛结论词，把“方便、效率、意义、优化”这类判断写成无证据的安全话。  
  问题：这是典型 AI 式正确废话。句子没有明显错误，但换成任何工具、任何作者都成立。  
  修法：删掉泛泛价值判断，改为回答：这个工具到底解决哪类配置痛点，原来的手工方案哪里不稳，为什么这个方案值得长期保留。

- `[missing-core-judgement]` 文风问题  
  位置 / 证据：前三节分别是“背景 / 使用方式 / 总结”，但只说“可以帮助用户完成配置”“按照步骤执行”。  
  问题：没有作者判断。HansBug 风格不是把步骤排一遍，而是先把问题坐标钉住。  
  修法：开头补一句明确判断，例如“这个工具的价值不在于少敲几行命令，而在于把配置过程里最容易散掉的前置条件、失败回滚和输出校验收束到一条链路里。”具体措辞可调整，但必须有判断主线。

- `[missing-boundary-section]` 文风与事实来源交叉问题  
  位置 / 证据：全文没有说明适用环境、版本、前置条件、不适用场景、失败方式。  
  问题：技术文没有边界就会把一次经验包装成普遍真理。  
  修法：补“本文解决什么 / 不解决什么”一节，说明工具面向什么配置、依赖什么环境、什么情况下不要照抄、失败时应该看哪些输出。

I 级问题：

- `[fact-source-weak]` 事实来源问题  
  位置 / 证据：“提升效率”“得到结果”“有意义”都是效果宣称，但没有输入材料、指标、案例或作者确认。  
  判定：没有编造作者项目经历，所以不是事实 C；但这些判断缺少支撑。  
  修法：要求作者补充真实工具背景、配置对象、使用前后的差异、失败案例或至少一个可复现例子。缺少材料时不要写成第一手结论。

- `[concept-split-missing]` 文风问题  
  位置 / 证据：候选稿把“方便”“有效”“完成配置”混在一起。  
  问题：没有拆开“能跑”“好用”“可维护”这几件事。  
  修法：至少拆一个关键对立：例如“能生成配置”和“配置可被复查、回滚、迁移”不是一回事。

- `[macro-logic-flat]` 文风问题  
  位置 / 证据：三节只是并列陈述，没有从问题、边界、方案、坑点、取舍走向最终判断。  
  修法：重排为“缘起与问题 -> 先说结论 -> 使用链路 -> 边界与坑点 -> 总结盖章”。

- `[heading-too-generic]` 标题太泛。  
  “背景”“使用方式”可以改成更带判断的标题，例如“为什么单靠步骤文档不够”“真正麻烦的是失败后的定位”。

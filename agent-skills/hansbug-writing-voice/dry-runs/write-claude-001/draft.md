本地仓库维护脚本，迟早会坏一次。这件事本身不可怕。可怕的是它坏完之后，没人知道接下来该往哪一步走。

很多脚本的失败现场写得很潦草：一个 traceback、一行红字、一段被切掉的 stderr，然后什么都不剩。下一个来收拾的人只能凭直觉猜——是网络抽风、是依赖坏了、是上一次手动改坏了 lockfile，还是脚本本身写错了。这种“猜”才是真正消耗时间的地方，而不是脚本本身那次失败。

所以这篇要说的判断很简单：本地开发脚本不需要写得不会坏，但必须把“坏之后该怎么办”写清楚。失败不是问题，失败路径模糊才是问题。

## 适用边界与不该套用的场景

这里只讨论一类东西：仓库维护脚本。

具体说，是那些只在维护者本地、或者本地 dev container 里跑，用来抓数据、生成索引、同步配置、批量改文件、跑构建预检的小脚本。它们的特征是：失败了顶多耽误维护者自己半小时，不会让任何线上服务停摆，也不会让任何用户感知到。

线上业务容灾不在本文范围里。线上系统的失败路径要谈重试策略、幂等性、熔断、回滚窗口、SLA 影响面，那是另一套讨论框架，不能拿仓库脚本这点小问题去硬套；反过来也一样，本文这套思路放到生产路径上就是玩笑。

需要继续往下读的前提是：你写的脚本，失败之后只影响你自己，而不是影响一整条线。

## 失败信息要交代到能直接动手的程度

脚本失败时打印的内容，本质上是写给“半小时后才来收拾这个烂摊子的自己”看的。判断一段失败信息够不够用，可以拿一个很苛刻的标准卡：维护者下次打开这个终端，能不能不用再读一遍源码就直接动手？

按这个标准看，常见的偷懒失败信息基本都不及格。只有一个 exception class 名字的，不及格；只有一行 “failed to fetch” 的，不及格；把 stderr 重定向到 `/dev/null` 然后只 `exit 1` 的，更不及格。这些写法表面上看起来“脚本已经报错了”，但等真出问题再回头看，里面没有任何能据此动手的信息。

够用的失败信息至少要把三件事说清楚：

- 它在做哪一步时坏的，不是哪一个函数，而是哪一个业务动作；比如“抓旧博客分类页第 7 页”比 “`fetch_page` 抛异常” 有用得多。
- 它当时手里握的关键参数是什么，比如目标 URL、目标文件、目标条目 id；这些参数不打出来，下次维护者只能自己再翻一遍代码反推。
- 它建议下一步做什么，哪怕这一步只是“重新跑一次”或者“先去检查代理变量再重试”；脚本作者写这一行的代价远低于维护者下次踩坑的代价。

## 边界、坑点与最容易写跑偏的地方

把失败路径写清楚，听起来朴素，真写起来最容易跑偏的就是几个地方。

第一个坑：把 try/except 当万能补丁。捕获异常不等于处理异常，更不等于把失败路径写清楚。一段 `except Exception: pass` 写得越漂亮，下次失败时维护者越抓瞎，因为连原始报错都没了。能让脚本“安静失败”的代码，在维护场景里几乎都是负资产。

第二个坑：把日志当成失败路径。日志可以辅助排查，但它不是给维护者的“下一步指令”。把所有信息都丢进日志文件，期待维护者去翻 `~/.cache/whatever/logs/2026-06-15.log`，本质上是在把工作推给下一个人。脚本对终端 stderr 说的那几行话，权重远高于落盘日志，因为那是维护者第一眼看到的东西。

第三个坑：把“失败”和“出错码 != 0”画等号。仓库维护脚本里有大量“半成功”的场景——抓到 80% 的页面、跳过了 3 个条目、写入文件时被另一个进程占用——这些不一定该 `exit 1`，但必须显式说明哪部分没做完，否则维护者就会默认它做完了。`exit 0` 加上一段被吞掉的警告，是仓库维护脚本里最隐蔽的一种 bug 源。

第四个坑：把失败路径写得过于热心。脚本不需要替维护者自动恢复一切，也不需要在失败时自动清理、自动回滚、自动重试三次。仓库维护脚本的恢复成本极低，自动行为越多，反而越容易把“为什么坏”这件事埋得更深。能让维护者一眼看清楚现场，比自动把现场打扫干净更重要。

## 收束：脚本可以坏，失败路径不能糊

回到最早那句判断：本地开发脚本不需要写得不会坏，但必须把“坏之后该怎么办”写清楚。

仓库维护脚本的真正成本，从来都不在“它失败了几次”，而在“每一次失败之后维护者需要花多少时间，才能重新对齐到一个可继续工作的状态”。脚本作者在写报错那两行的时候，是在替未来的自己省时间；省下来的时间，多到不成比例。

再往上抬半层看，这件事的本质不是“写更详细的报错”，而是默认假定脚本会失败，然后把失败当成一条正常路径来设计——不是异常分支，不是兜底逻辑，是和成功路径同等地位的另一条主流程。一个把失败当主流程对待的脚本，长期看几乎一定比一个写得很努力、却只在心里默念“应该不会出错”的脚本更耐用。

至于“如果有一天这个脚本要被搬到线上去跑”——那时候要重写的东西远不止失败路径，本文这套思路也就不再适用了。

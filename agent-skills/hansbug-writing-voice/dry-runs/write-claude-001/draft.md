写脚本这件事，凡是亲手维护过一个会持续跑半年以上的小仓库的人，大概都心里有数：脚本本身写出来不难，难的是它哪天炸了之后，你还认不认得它。

闲话先收一收。本文说的“脚本”，特指个人技术博客这类仓库里的维护脚本：抓旧站索引的 `fetch_old_blog.py`、构建命令 `npm run build`、CI 触发的部署、偶尔手跑的标签整理小工具，诸如此类。我不会把它扯到线上业务的容灾、报警阈值、SLO 这些方向去；那是另一个量级的话题，硬塞进来只会两边都讲不透。

先把判断亮在前面：**脚本失败本身一点都不可怕，可怕的是失败之后没有一条清晰路径**——下一个打开它的人（往往就是三个月后失忆的自己），看不出它到底卡在哪一步、应该回到哪一步、能不能安全重跑。

## 失败路径到底指什么

“失败路径”这个词，听上去像在讲容错系统，其实在维护脚本这个语境里非常朴素。它不是要让脚本不挂，而是要让脚本挂掉之后的那十分钟里，维护者能完成这三件事：

- 一眼看出失败在哪一步，而不是在二十行 traceback 里大海捞针；
- 一眼看出失败的副作用边界，例如是只读一半，还是已经写坏了一半；
- 一眼看出下一步该做什么——重跑、修参数、还是先回滚某个中间产物。

把这三件事拆开看，会发现它们其实对应脚本里三个非常具体的写法层面：日志、原子性、退出语义。看起来是“工程细节”，本质上是“脚本愿不愿意把自己交代清楚”。

不是“写了 try/except”就算考虑了失败路径，而是失败发生时，脚本是否还在替读者说人话。这两件事并不是同一件事，很多脚本在这个地方偷懒，写了一堆 `except Exception: pass`，看起来很健壮，实际上是把灯关了再说没看见炸。

## 怎么把失败路径写清楚

按维护脚本的尺度，下面这几条基本够用，不必上升到框架。

第一，**日志要分清三类信息**：我正在做什么、我刚才做完了什么、我为什么失败。三者各自一行，不要混在一句里。一个长期能维护的脚本，关键节点之间的日志会自带一种“接力感”——上一行说“准备开始抓 X”，下一行说“X 抓完，Y 条”，再下一行才轮到错误信息。出错时，看上一条成功日志就能立刻定位到失败发生在哪两步之间。

第二，**写操作必须自带边界声明**。脚本一旦要落盘，就要提前讲清楚“我要写哪个文件、要不要先备份、失败时要不要回滚”。哪怕只是一句注释或一个 dry-run 开关，也比裸 `open(path, "w")` 强得多。仓库里的 `fetch_old_blog.py` 会同时更新 `src/data/oldBlogCatalog.json` 和 `.ts` 两个产物——这种多产物脚本如果失败在第二步，第一步留下的半成品就是隐性陷阱。把“写入是原子的还是非原子的”说清楚，比事后排查省得多。

第三，**退出码和退出信息要对得上**。脚本应当只在真正“没干完”时返回非零；只在真正“干完且产物可用”时返回零。中间态——例如“抓到了 200 条但还有 50 条失败”——要么显式选择失败退出，要么显式打印一行总结让 CI 看见，不能含糊地“静默通过”。一条规则：**stdout 是讲给读者听的，exit code 是讲给 CI 听的，两边都不能糊**。

第四，**失败信息里要带可执行的下一步**。最差的失败信息是只说“出错了”；稍好的会带 traceback；真正好的会顺手告诉维护者“你大概率应该 `rm -rf .cache/old-blog && rerun`”或者“先检查代理是否在 `$https_proxy` 里”。这一步几乎是 0 工程成本，但能把后续维护成本压低一个量级。

## 边界与坑点

把上面这些话搬到线上业务系统，会立刻露怯。线上业务关心的是**多副本一致性、降级、限流、熔断**，那是另一个工种的话题；本地脚本谈这些反而过度工程。所以这套写法只在以下边界内成立：

- 一次运行只对应一个维护者，不存在并发竞争；
- 失败的代价主要是“浪费时间”，不是“伤害用户”；
- 重跑是廉价的，不存在跑一次扣一次费用的外部副作用。

如果你的脚本恰好踩到了边界之外，例如开始往外网发邮件、调付费 API 或推送公开制品，那就不是“写清楚失败路径”的问题，而是“这个脚本一开始就不该这么轻量地写”的问题。

还有几个常见坑点也提一下：

- **过度 try/except**。把所有异常吞掉，最后脚本永远 exit 0，看起来很稳，其实是把失败藏起来。日积月累，CI 通过率会变成一个没有意义的指标。
- **日志一上来就 DEBUG 级**。一个一年才跑十次的维护脚本，关键节点用 INFO 就够；上来铺一堆 DEBUG，反而让真正重要的失败行被淹没。
- **失败后留下半成品文件没收拾**。最难复现的不是错误本身，是“上次跑到一半留下来的奇怪状态”。这类状态在第二次运行时往往伪装成新错误。
- **重跑不是幂等的**。脚本第一遍跑出错，第二遍跑居然又生出新的错——这种就不是“失败路径不清楚”，而是失败路径里埋了二次伤害。维护脚本的幂等性是这套写法的隐性前提，不幂等就先把这一条修了再谈别的。
- **【需要作者补充：一次真实踩坑现场，例如某个本地脚本失败后误覆盖了什么、用了多久才查清楚】**。这里如果有具体案例，整篇文章的说服力会再上一截；当前为保持事实稳健暂缺。

## 总结

说到底，本地维护脚本和线上系统的差别没那么神秘：前者只是后者的低配近亲。但低配不代表可以糊弄——恰恰因为没人替你兜底，脚本本身就必须把“失败之后怎么办”这件事写在自己身上。

归根结底，一个写得好的维护脚本，不是“永远不会挂”的脚本，而是**挂了以后，连半夜被它叫起来的那个未来的维护者，也能在三分钟内看明白发生了什么、能不能放心重跑**的脚本。失败本身从来不是问题，失败之后留下的那条路径有没有写清楚，才是。

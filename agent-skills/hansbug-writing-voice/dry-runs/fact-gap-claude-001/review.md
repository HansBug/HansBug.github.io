C 级问题：
- [C-fabricated-experience-1] 位置：原草稿“背景”节首句。证据：“笔者曾经在一个大型项目现场负责过脚本治理”——无任何来源、项目名、时间。
  修复建议：改为“需要作者补充真实项目名、时间窗口与可公开语境”，在作者补料前不得作为事实出现。
- [C-fabricated-meeting] 位置：原草稿“背景”节第二句。证据：“当时团队内部开会决定统一改造所有工具”——无会议时间、产出、决议形态。
  修复建议：改成占位请求，或退化为非第一手的“一般而言这类决策的常见做法”，并明确这是推断而非作者经历。
- [C-fabricated-launch] 位置：原草稿“方案”节首句。证据：“我们上线过一套完整流程”——无 changelog、PR、仓库或文档。
  修复建议：在作者补可公开的上线证据之前，不能写成既成事实；本轮按“需作者补充上线材料”处理。

I 级问题：
- [I-no-boundary-1] 位置：原草稿“背景”节末句。证据：“只要提前规范脚本，后续就不会出问题”——把单次经验写成普遍真理，没有失败方式和边界。
  修复建议：补“在哪些场景下成立 / 哪些场景下会失效”，把"不会出问题"降格为"能挡住哪一类问题"。
- [I-no-boundary-2] 位置：原草稿“方案”节。证据：“建议所有项目都直接照搬”——无差别推广，没有规模、技术栈、团队结构等边界。
  修复建议：把适用前提写清楚，承认照搬通常不成立；保留判断主线即"脚本治理是取舍"。

M 级建议：
- [M-title-flat] 位置：三个二级标题“背景 / 方案 / 总结”。证据：标题只说功能不说判断。
  修复建议：可改为“先把缺口说在前面 / 把我们上线过改成可验证表达 / 脚本治理不是一次性做完的事”这类带判断的标题（修订稿已采用）。

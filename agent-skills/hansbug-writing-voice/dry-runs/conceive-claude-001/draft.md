文章类型：技术实践文（按 article-archetypes.md 的"技术实践文"骨架推进）

主问题：在个人技术博客仓库里，怎样把一个原本"随手写"的临时脚本，改造成后续 agent 和作者本人都能放心维护、放心修改、放心继续跑的仓库内工具，而不是让它停留在"当时跑得动、半年后没人敢碰"的状态。

不解决：
- 不解决具体业务领域脚本（爬虫、ETL、ML 训练）的内在算法或性能问题。
- 不解决要不要把脚本换成 Rust / Go / Bash 这种语言层选型问题；本文默认已经确定继续在 Python 范围内维护。
- 不解决 CI 平台、容器镜像、私有依赖仓的运维问题。
- 不解决"要不要写脚本"这一前置问题；本文从"脚本已经存在并且会继续被用到"开始谈起。

核心判断：临时脚本能否长期活下去，关键不在功能多寡，而在三件事——入口稳定、副作用可见、失败可读。任何一件偷懒，脚本就会在几个月后变成"没人敢删也没人敢改"的暗雷，比当初不写还麻烦。换句话说，"能跑"只是最低门槛，不是"设计成立"的证据；很多被我们叫做"临时脚本"的东西，事实上早就在被仓库默认状态托管，只是它的维护者还没意识到自己已经在维护一个工具。

读者应该先看：
- 如果只想要可执行配方，直接看建议结构里的"我的方案"（即第 4、5 节）；
- 如果在犹豫要不要把自己的临时脚本仓库化，重点看"为什么旧做法不够"和"坑点与边界"；
- 如果是后续 agent 接手别人留下的脚本，重点看"失败可读"和"反例 / 坑点"。

建议结构：

1. 缘起 / 破题：从一个非常普通的场景切入——某天打开仓库想再跑一次几个月前那个"随手写的脚本"，发现自己也看不懂它当时到底在干什么、为什么传那几个奇怪参数、为什么 cache 落在那个目录。半口语带读者进入"临时脚本陈旧化"这个具体处境，再迅速收回正题：不是脚本写得烂，而是它一开始就没按工具维护，于是它的腐烂是结构性的，不是偶然事故。

2. 问题定义 / 边界：明确判断坐标——本文不问"它现在能不能跑"，只问"三个月后另一个 agent 或作者本人接手时，敢不敢直接信任它"。范围限定为仓库内 Python 维护脚本；明确把"一次性数据迁移、几乎不会再跑"的脚本排除在本文之外，那种东西的最佳归宿是 commit 留档而不是工具化。这一步同时给出"什么算是仓库内工具"的最低成立条件，让后文的批判有坐标。

3. 核心判断前置：直接把上面那条"入口稳定 / 副作用可见 / 失败可读"判断亮出来。不留悬念，不拖到结尾。这是按 macro-logic.md 里"核心判断前置"那条轨道做的，目的是让读者在前三屏就抓到论点，后面读到任何一段都知道它在论证哪一条。

4. 分维度分析（每个维度都要落到"为什么这样做更合理"，不能停在"怎么做"）：
   - 入口稳定：脚本必须有明确放置位置（`scripts/` 或 `tools/` 之类的稳定目录，而不是随手扔在仓库根目录）；必须有 `--help`；必须用命令行参数描述行为，不要靠 README 解释怎么手改 `sys.argv`；脚本入口位置一旦确定，不要随兴趣搬动。
   - 副作用可见：脚本对外界做了什么——写哪些文件、改哪些目录、是否联网、是否动 cache、是否调用付费 API——必须能通过 `--dry-run` 提前看到；这一节的判断句要硬：副作用不可见的脚本不算工具，是地雷。
   - 失败可读：失败时必须告诉读者下一步该怎么办，而不是抛一坨 stack trace 就完事；错误信息里要带具体路径、具体字段、具体缺失原因；缺依赖时直接告诉读者怎么装。这条直接对标本仓库已有脚本（如 `lint_voice_references.py`、`check_hansbug_voice.py`）已经表现出的方向。
   - 维护视角：脚本可被 lint / type-check / 至少一个 smoke test 覆盖；不要写成"全在一个文件里 800 行 main 函数"；同时要警惕反向陷阱——为了显得正式硬塞 framework，把 30 行脚本拆成 5 个模块同样不可取。

5. 反例 / 坑点（按 macro-logic.md 的"反例与边界"那一节处理）：
   - 不要为了升级而强行加 framework；`argparse` 在多数维护脚本上已经够用，不要为了显得"正式"上 `click` / `typer`，更不要为了显得"工程化"做依赖注入。
   - 不要把副作用伪装成"幂等"。如果它会覆盖文件、改 cache、改 git 状态，必须明说；要破坏性动作就配 `--force`，并且默认不开。
   - 不要把临时 cache 硬编码在 `~/`；优先走仓库内 ignored 目录或 XDG 规范，方便后续 agent 在隔离环境里跑。
   - 不要把 secret / token 写成脚本默认值；走环境变量或系统 keyring（参考全局 `CLAUDE.md` 里关于 BUAA mail 走 keyring 的策略，那是同一类工程纪律）。
   - 边界：如果脚本只是"一次性数据迁移、一年内大概率不会再跑"，仓库化反而是过度工程；这种东西的正确归宿是一次性 commit + 详尽 commit message，而不是被打扮成工具。
   - 反向反例：也要承认有些临时脚本就该死，不该被升级；维护它会消耗的精力远大于它带来的价值。这一段的存在是为了避免文章变成"一切都该工具化"的传教稿。

6. 总结盖章：脚本之所以会变成暗雷，不是因为作者偷懒，而是因为大家默认"临时"就等于"免维护"。事实上，仓库里活下来的脚本几乎一定不是临时件，而是被仓库默认状态托管的"事实上的工具"——它的功能也许临时，但它的存在已经不临时了。把它当工具维护，不是工程洁癖，是对未来的自己和后续 agent 最低限度的尊重。最后一句要落锤，让读者明白：所谓"临时脚本"，往往只是作者还没承认自己在维护它而已。

事实缺口：
- 缺真实项目现场：作者本人是否真的遇到过"几个月后看不懂自己写的脚本"的具体事件，发生在哪个脚本上，需要作者补一个真实场景；否则缘起一节只能写成一般工程经验，不能写成第一人称踩坑回忆。
- 缺正面 / 反面例子：本仓库现有维护脚本（如 `scripts/fetch_old_blog.py`、`agent-skills/hansbug-writing-voice/scripts/*.py`）如果要被本文当作"已经按三件事维护"或"还差什么"的活样本，需要作者点名授权用哪一个、能不能公开它当时哪一处不达标；构思阶段不能替作者替这些脚本盖章。
- 缺线上反馈数据：是否有真实的"另一个 agent 三个月后改我脚本被坑"的具体记录；如果没有，结尾的方法论判断必须降格写成"笔者的工程倾向"，不要写成"实践已经证明"。
- 缺 CLI 框架偏好：如果正文要给具体命令（`argparse` vs `click` vs `typer`），需要作者确认目前仓库倾向；否则只能写成"这一层选什么都行，重点不在这里"。
- 缺 dry-run 实例：要让"副作用可见"这一节有重量，最理想是给一段真实脚本的 `--dry-run` 输出片段；这需要作者从现有脚本里挑一段授权。

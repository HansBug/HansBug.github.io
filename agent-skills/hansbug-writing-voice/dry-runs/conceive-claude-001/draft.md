文章类型：技术实践文

主问题：在个人技术博客这种长期演化的仓库里，怎么把一个一次性写出来的临时维护脚本，改造成后续 agent 和作者本人都能放心碰的“仓库内工具”——重点不是“这脚本能不能跑”，而是“半年后再回来时，它会不会反过来咬人”。

不解决：
- 不教读者怎么从零写脚本，也不科普 Python / Node 标准库 API。
- 不覆盖通用的“CLI 框架选型横评”，不打算把 argparse / click / typer / commander 之类做对比。
- 不讨论把脚本搬到独立 PyPI 包、发独立 CLI、做 monorepo 拆仓这类“升级到产品”的方向；本文只处理“留在仓库里”的中间形态。
- 不解决 CI/CD 接入、发布流水线、跨仓库分发等链路问题，那是另一篇的范围。

核心判断：临时脚本和仓库内工具不是同一种东西的两个阶段，而是两类性质不同的产物。前者优化的是“此刻把活干完”，后者优化的是“未来任何一个 agent 或作者本人来碰它时，不需要重新读懂作者当时的脑回路”。判断一段脚本是否已经过线，不看它能不能跑，看的是：它的入口、参数、副作用、失败方式和退出码，能不能在不读源码的前提下被另一个人或另一个 agent 安全调用。能跑只是最低门槛，不是设计成立的证据。

读者应该先看：开头三段式 quick-start（让能直接把任务丢给 Codex / Claude Code 的读者先撤）+ 第 3 节“核心判断前置”。如果只关心“为什么不能继续按临时脚本糊下去”，看到第 4 节就可以停。

建议结构：

1. 缘起 / 破题：从一个非常常见的现场切入——仓库里多了一个 `scripts/fix_xxx.py`，当初十几行写完就跑，半年后再回来时，作者本人都要先 `head -n 50` 才敢动它，更别说让 agent 自动调度。这里只破题，不展开。紧接着按 `CLAUDE.md` 固定模板给出三段式 quick-start 引用块：第一段固定句式声明本文范围与边界；第二段把“帮我把 `scripts/` 下这个临时脚本改造成可维护的仓库内工具”这一类指令打包成可复制 prompt，里面用 `{{PAGE_URL}}` 指回本页；第三段固定句式邀请关心取舍 / 边界 / 长期维护判断的读者继续。

2. 问题定义 / 边界交代：明确本文只谈“留在仓库里的脚本工具”，不是独立 CLI、不是包、不是服务。把场景钉在“个人技术博客仓库的维护脚本”这种小而真实的范围，并说明为什么这个范围反而最容易出问题——它既没小到可以一次性丢掉，也没大到值得为它单开仓库，正好卡在最容易被糊弄的中间态。

3. 核心判断前置：把上面那段“能跑不是设计成立”的判断直接亮出来，并把“临时脚本 / 仓库内工具”这两个概念硬掰开。表层差异是“有没有 argparse”“有没有 README”，本质差异是这段代码的服务对象到底是“此刻的我”还是“未来任何一个会读到它的人或 agent”。这里要点名一个常见误判：很多人以为加几个 `--help` 就算工具化了，其实只是把临时脚本套了层壳。

4. 分维度展开分析（这一节是论证主力）。预计四个维度，每个维度都不是“做什么”，而是“为什么是这件事在区分两种产物”：

   - 入口与参数：是否有稳定、可被外部调用的 CLI 入口；参数名是否能脱离作者记忆被理解；必填和可选是否能在 `--help` 里看清；默认值是否在源码、文档、CLI 三处一致。判断句：参数不是给作者自己用的，是给“半年后的某个人或某个 agent”用的。
   - 副作用与可回退性：脚本到底改了什么（文件系统、git 状态、cache、远端资源），有没有 `--dry-run`，失败到一半时是否有可恢复的中间状态。判断句：一个不能空跑的脚本，就是一个不能审阅的脚本。
   - 失败方式与退出码：是否区分“用户用错了”“环境不对”“目标本来就不该处理”“真的炸了”这四类情况；退出码是否被 CI 或别的 agent 安全消费。判断句：默认 `exit 0` 是对未来最大的不负责任。
   - 文档与发现性：`README` 或 `scripts/README.md` 是否能让人“不读源码就敢用”；仓库 `CLAUDE.md / AGENTS.md` 是否登记了这个工具的存在、用途和边界；是否有最小自检命令。判断句：一个仓库内工具如果在 `AGENTS.md` 里找不到入口，它对 agent 来说就等于不存在。

5. 反例 / 坑点 / 边界（倒数第二节，处理真正难的地方）：
   - 反例一：过度工程化。给一个十几行的 cache cleanup 脚本套上完整的 `subcommand + plugin + 配置文件 + 日志框架`，最后没人再敢改它。判断句：仓库内工具的成立条件是“后续维护成本不超过它带来的收益”，过度工程化是另一种偷懒。
   - 反例二：伪装工具化。只把 `if __name__ == '__main__'` 改写、加几行 `argparse`，但内部仍然写死路径、写死作者本机环境。这种最迷惑人，因为表面上已经“像”工具了。
   - 坑点：脚本之间的隐式依赖（A 必须在 B 之后跑、必须先 `npm run build`），如果不在入口处显式表达，就是给未来挖坑。
   - 边界：本文方案不适用于“一次性的数据迁移脚本”——那种确实就应该用完即弃，不要逼自己工具化；以及不适用于“高频被多人调用”的工具，那类应该升格成独立包。

6. 总结盖章（结尾上升半层）：把“怎么改造一个脚本”收束到一个更稳定的判断——仓库内工具的真正考验不在写它的那天，而在半年后第一次有 agent 自动调度它的那一刻。把视角抬到“agent-friendly 的工程纪律”：未来越来越多的活会被 Codex / Claude 之类的 agent 接手，仓库里每一个不能被 `--help` 讲明白的脚本，都是一颗早晚会被踩到的雷。结尾句要带落锤感，不能停在“希望对大家有帮助”。

事实缺口（必须由作者补充，不能编造）：
- 【需要作者补充】本文是否要绑定一个具体脚本作为贯穿全文的例子。当前抽象场景下只能写成一般工程取舍；如果作者愿意拿本仓库里某个真实脚本（比如 `scripts/fetch_old_blog.py` 或本仓库 PR-5 forward-test 用到的某段维护脚本）当主线，叙述强度会高很多。这里 agent 不替作者选。
- 【需要作者补充】是否有真实“被自己写的脚本咬到”的现场可以引用（例如某次因为没有 `--dry-run` 误删 cache、某次因为退出码总是 0 让 CI 没报警）。没有现场，就只能写成“一般来说会怎样”，文章会缺一段最有作者味道的复盘。

## 对原稿的 C/I/M 判定

本次是 issue #25 的反向压力测试，目标不是给某个真实工具背书，而是专门验证 `fix-ai-cliche` 能不能把一段“看着像 HansBug，实际全是贴纸”的草稿拆出来、改回去。执行入口已经按 `CLAUDE.md` 与 `agent-skills/hansbug-writing-voice/SKILL.md` 走完，使用的是 `codex` CLI dry-run 场景。

先说结论：原稿是 C=3 / I=0 / M=2。

C 级问题有三类。第一，高口癖密度 + 低判断密度：它把“咳咳”“笔者”“好吧”“2333”堆在句子里，但没有说明作者到底赞成什么、反对什么、为什么这样判断。第二，无边界：它没有交代本文解决什么、不解决什么、适用什么输入，也没有说明失败方式。第三，AI 腔正确废话：它用一串安全、空泛、不会出错的套话把问题糊过去，读完只知道“这个东西好”，不知道“它好在哪里，坏在哪里，什么时候不该用”。

M 级建议有两条。标题只写“背景 / 方案 / 总结”，信息功能太弱；最后一段只做礼貌收尾，没有把判断压回长期维护或写作流程的取舍上。

## 本文真正要修的是什么

本文解决的是一个很窄的问题：当一段中文技术博客草稿已经露出明显 AI 腔、又试图用 HansBug 式口癖遮过去时，应该怎么把它改成有主问题、有边界、有判断的正文片段。

本文不解决工具本身是否好用的问题，也不假装已有作者亲历案例。用户没有提供真实案例、环境记录、对话材料或第一手体验，所以这里不能补成确定事实。缺少事实，就把事实缺口摆在桌面上。别拿故事性冒充证据。

核心判断也很简单：这类草稿最该修的不是语气，而是骨架。口癖删掉一半，判断补上两层，边界讲清楚，文章才可能站起来。否则它只是把几句旧博客味的词贴在 AI 说明文外面，热闹得很，里面是空的。

## 为什么口癖救不了这段草稿

“像 HansBug”不是多写几次“笔者”，也不是在结尾扔一个“2333”。这些东西只能做调味，不能当主菜。原稿的问题恰恰在这里：它把调味料倒了一锅，却没有菜。

真正需要补的是判断坐标。比如这个工具到底用来处理什么链路？它提升的是人工检索成本、配置迁移成本，还是审稿返工成本？它的收益来自自动化，还是来自把边界提前写清？这些问题不回答，所谓“效率提升”就只是一个空壳词。

所以修复时要先把“能用”和“值得写进长期流程”拆开。能用只说明它跑得起来；值得长期维护，才说明它在失败时可诊断、在交接时可解释、在换人后还能被继续使用。两者不是一回事。

## 边界与坑点先摊开

这段修复稿只适用于 issue #25 这种反向压力测试：输入文本短、事实材料少、目标是暴露文风 gate 对 AI 腔和口癖堆砌的识别能力。它不适用于已经有大量真实材料的长文改写，也不适用于需要补充作者第一手经验的复盘文章。

坑点有两个。第一，不要为了让文章显得有现场感而编故事。没有作者补充的真实经历，就只能写“需要作者补充”，不能把猜测包装成回忆。第二，不要把机械 gate 当成最终审美裁判。脚本能抓住明显的空话、缺边界、缺收束，但它不能替作者判断一篇文章是不是真的有洞察。

说白了，gate 是门槛，不是作者本人。把门槛过了，只说明这段文字没有在最硬的地方摔倒；要写得有分量，还得继续补事实、补取舍、补真实经验。

## 总结盖章

这次 issue #25 的反向压力测试，真正测的不是某个词能不能出现，而是 agent 会不会把文风误解成口癖按钮。原稿失败，失败得很典型：话很满，判断很薄；语气很像，骨架没有。

修复后的方向也很明确：先定主问题，再划边界，再下判断，最后把失败方式和长期维护取舍讲清楚。口语化表达可以留下几处，但只能在逻辑站稳之后出现。

归根结底，HansBug 式技术写作不是给 AI 文本贴一层旧博客滤镜。能把问题拆开、把边界讲透、把判断钉住，才算真正开始写文章。

最近这段时间，笔者又被一个老问题反复追着打：为什么很多技术教程看起来很努力，命令、参数、背景、链接、截图一个不缺，读者照着走却还是一脸懵？

这事最烦人的地方在于，它通常不是“作者不认真”。恰恰相反，很多坏教程坏在作者太认真：怕读者不知道背景，于是先讲架构；怕读者以后查不到参数，于是把 reference 摊开；怕读者遇到真实任务，于是顺手塞几个 how-to 分支；怕文章不够有深度，于是又补一段设计哲学。最后就变成那个经典的“面多加水，水多加面”：背景多了补步骤，步骤多了补解释，解释多了补索引，索引一多又觉得缺少引导。作者越补越勤快，文档越补越臃肿，入口只剩一团发胀的面糊。

所以本文真正要讲的不是“技术文档怎样写得体面”，而是一个更硬的问题：**当我们说一篇 tutorial 是合格的，它到底应该满足什么结构、边界和验收条件？**

先把结论拍在桌上：**tutorial 的核心不是资料完整，而是学习路径成立。** Reference 负责查准事实，how-to guide 负责完成任务，explanation 负责建立理解，而 tutorial 负责带读者获得第一次可重复的理解。把这四件事混成一件事，看起来像照顾读者，实际上是在把读者按进信息泥潭里游泳。

本文会先做一点技术考古，解释我们为什么总把 tutorial 写成 reference、HOWTO、架构说明或者 CI 示例清单；然后用 Diátaxis 四象限把读者动作拆开；最后回到 tutorial 主战场，给出一套可以进入 PR review 的结构、验收和反模式清单。换句话说，这不是一篇“大家应该学习 Diátaxis”的导读文，也不是一篇完整的文档工程手册。本文只盯住一件事：**怎样写一篇真的能带读者走通第一条学习路径的技术教程。**

如果只想拿走一句话，那就是：教程不是把作者知道的东西摊开，而是把读者带到能自己继续走的地方。前者叫资料堆放，后者才叫教学设计。

## 一点技术考古：为什么我们总把 tutorial 写成 reference

很多 tutorial 写坏，不是因为作者脑子里没有结构，而是因为技术文档本身就继承了几条不同传统。每条传统都很强，每条传统也都很有用；麻烦在于，它们解决的是不同读者动作。一旦作者把这些传统的优点一股脑塞进同一条学习主线，教程就会从“带读者学会”退化成“把材料都扔给读者”。

这一节不是要写一部技术文档史。笔者没有这个野心，也没必要在一篇教程写作文章里把历史长河捞个底朝天。这里做的只是小规模技术考古：沿着 manual / HOWTO / literate programming / notebook / docs-as-code 这几条线，看清楚今天的混乱到底是怎么来的。

为了避免“技术考古”变成空话，下面每条传统都放一个很小的真实切片。这里优先用摘录而不是截图，一是避免远程图片热链和版权麻烦，二是让读者直接看到那类文档的语言骨架：它当年到底在承诺什么，又为什么容易被我们误搬进 tutorial。

### Manual / man page：查准事实的强传统

最早必须提的是 manual / man page 这一类 reference 传统。1971 年第一版 Unix Programmer's Manual 已经把用户命令、系统调用、子程序、特殊文件、文件格式、维护命令等内容分门别类组织起来[@unix_programmers_manual_1971]。这个传统的核心承诺非常清楚：当用户要查一个命令、接口、文件格式或者系统边界时，文档必须准确、完整、可扫描、可查证。

> 考古切片：1971 年 Unix Programmer's Manual 的下载目录按 “Commands, part 1”“System calls, part 1”“Library routines”“File formats” 这类对象组织内容[@unix_programmers_manual_1971]。

这个切片很有味道。它不是按“新手第一小时应该怎样进入 Unix”来排，而是按系统对象和事实类别来排：命令归命令，系统调用归系统调用，库例程归库例程，文件格式归文件格式。换句话说，它的第一秩序不是学习路径，而是事实索引。读者已经知道自己要找哪一类东西时，这种组织方式非常强；读者还不知道自己该先摸哪一块时，它就会显得冷。

这类文档的价值不需要辩护。没有 reference，技术系统就像没有地图的城市。你当然可以凭记忆在熟悉街区里转悠，但只要进入陌生区域，缺少稳定事实索引就会很痛苦。

问题在于，manual 的成功逻辑很容易被误搬到 tutorial 里。作者一想：“这个参数读者迟早要知道，这个概念也很重要，这个接口的全部选项最好也列一下。”于是教程刚开头就堆出一张参数表，读者第一步还没走，先被完整性糊了一脸。

Reference 的完整性是优点，tutorial 的完整性经常是陷阱。Reference 面向的是“我已经知道自己要查什么”；tutorial 面向的是“我还不知道这个系统该怎么进入”。两者的读者状态不一样，写法当然也不该一样。

说白了，manual 像字典，tutorial 像带路。字典当然要全，带路则不能把整座城市的道路编号都背给第一次来的人听。否则你不是在带路，是在给人现场朗读市政档案。

### HOWTO：把事情配置出来的实用传统

另一条很强的传统是 HOWTO。Linux Documentation Project 保留下来的入口，以及单独的 Guides 列表，能清楚看到这类文档在开源世界里的位置[@linux_documentation_project; @linux_documentation_project_guides]。HOWTO 的气质非常实用：读者现在有一个具体问题，需要把某件事配置出来、跑起来、修好、迁走或者接上。

> 考古切片：LDP 页面导航里 HOWTOs、Guides、FAQs、man pages 并排出现；其中 Advanced Bash-Scripting Guide 又自称 “both a tutorial and a reference”[@linux_documentation_project_guides]。

这个切片比单纯说“HOWTO 很实用”更能说明问题：早期开源文档本来就经常把教程、指南、FAQ、手册、参考资料放在同一个公共入口里。Advanced Bash-Scripting Guide 这种自我描述也很诚实——它确实想同时做教材、手册、自学材料和 reference。对一本书来说，这未必是罪；但对一篇 tutorial 来说，这种承诺如果不拆开，读者路径就很容易被压扁。

这类文档救过很多人的命。凌晨两点网络坏了，服务起不来，内核模块加载失败，双系统引导炸了，你当然不想先读一篇“操作系统哲学导论”。你想要的是：告诉我当前条件、步骤、验证方式和常见错误，先把事情做成。

HOWTO 的危险也在这里：它太实用了，以至于作者很容易把“任务完成”误认为“学习成立”。一个 HOWTO 可以把读者带到某个任务的终点，但这不等于读者获得了稳定心智模型。读者可能照着做完了，却不知道刚才哪个步骤解决了哪个问题；下一次环境稍微变一变，他就又回到原点。

这不是 HOWTO 的错。HOWTO 本来就不负责完整学习，它负责现实任务。错的是把 HOWTO 的任务逻辑当成 tutorial 的学习逻辑。一个教程如果只按任务推进，却没有阶段自检、概念连接和反馈设计，读者学到的很可能只是“这串命令在作者环境里曾经有效”。

这种状态在工程现场特别常见：团队内部沉淀了一堆“照这个做”的页面，短期看很有效，长期看新人永远只能复制粘贴。页面没有坏，但人的理解没有长出来。请各位想想看，这不就是技术债换了一件文档外套吗？

### Literate programming 与 notebook：代码也可以按理解顺序组织

再往另一边看，还有 literate programming 和 notebook 这条叙事传统。Knuth 谈 literate programming 时，强调的不是把代码变成文学装饰，而是让程序按人的理解顺序呈现，让解释和实现形成一套可读结构[@knuth_literate_programming]。Jupyter 这类 computational notebook 则把叙事、代码和输出放在同一个计算叙事容器里，Project Jupyter 对这一点也有过系统说明[@jupyter_computational_narratives]。

> 考古切片：Knuth 页面把 literate programming 描述为把程序当作 “a piece of literature”，而且是 “addressed to human beings”[@knuth_literate_programming]；Project Jupyter 则描述了能组合 “live code, equations, narrative text” 的 notebook[@jupyter_computational_narratives]。

这两个切片合在一起看，风格就很清楚：代码不再只是机器吃掉的指令，而是可以被人阅读、被人复现、被人沿着思路走下去的叙事材料。它们给 tutorial 的启发非常大，因为教程也需要“按人的理解顺序”组织动作和解释。可问题也藏在这里：叙事一旦太有魅力，作者就会忍不住把每个旁支都写得像主线。

这条线对技术写作的启发很大。代码不是只能作为“复制进去执行”的材料，它也可以承担解释功能：为什么先定义这个变量，为什么这个输出说明模型已经连上，为什么这一步之后可以进入下一层抽象。对于数据科学、机器学习、数值计算这类领域，notebook 式叙事甚至直接改变了很多人写教程、写实验记录、写技术报告的方式。

但是，叙事能力强不等于 tutorial 可以无限解释。恰恰相反，解释越强，越容易抢走学习路径。作者一旦沉迷“这里其实还可以展开讲讲”，读者就会在还没看到第一个可观测反馈之前，被背景、历史、哲学、设计权衡和作者灵感小作文轮流轰炸。

这类文章读起来往往很“有深度”，但新手跟不下来。它像一位很有学问的导游，刚进景区大门就开始讲地质年代、历史变迁、建筑风格、旅游经济和个人审美。内容都对，时机全错。

Tutorial 当然需要解释。问题不是要不要解释，而是解释什么时候出现、解释服务哪一步、解释是否帮助读者确认刚刚建立的理解。解释必须服从当前学习路径，否则它就是披着知识外衣的支线任务。

### Docs-as-code：文档进入工程链路

最后是 docs-as-code 和可验证文档传统。Write the Docs 对 docs-as-code 的介绍，核心是把文档像代码一样纳入版本控制、评审、自动化和协作流程[@write_the_docs_docs_as_code]。Sphinx 提供 doctest 扩展，可以对文档中的交互式示例进行测试[@sphinx_doctest]；Rustdoc documentation tests 可以让文档示例进入测试语境[@rustdoc_documentation_tests]；GitLab 文档则把链接、lint、Vale、图片路径等检查纳入文档测试链路[@gitlab_documentation_testing]。

> 考古切片：Write the Docs 对 docs-as-code 的工具枚举很直白：Issue Trackers、Version Control、Code Reviews、Automated Tests[@write_the_docs_docs_as_code]。

这个切片说明 docs-as-code 的气质不是“把文档写得更漂亮”，而是把文档拉进工程流水线。文档不再是发布后某个人顺手补的附件，而是可以走 issue、走 git、走 review、走自动化检查的工程对象。这对 tutorial 很关键，因为教程里的命令、输出、链接、图片和版本都会坏；但它也会制造另一个误会：流程越完整，作者越容易以为学习路径也被证明了。

这条线非常重要，因为它把“文档会坏”这件事从道德问题变成工程问题。以前文档坏了，常见说法是作者不够认真；进入 docs-as-code 之后，至少有一部分坏法可以被自动拦住：示例编译不过、链接失效、格式破坏、图片路径错、术语不一致、交叉引用断掉。这些都不应该靠读者替我们踩雷。

但这里也有一个边界：机器能证明材料没坏，却不能单独证明学习路径成立。Rustdoc 可以证明示例代码还会编译，GitLab 的文档测试可以证明链接和格式还过关，Sphinx doctest 可以证明某些输出符合预期；它们都很有用，但它们不知道一个目标读者在第 3 步为什么停住，也不知道读者看完后是否能独立复现。

换句话说，docs-as-code 解决的是“材料是否腐烂”的一部分问题，不直接解决“教学路径是否成立”的全部问题。把 tutorial 接进 CI 很好，但如果教程本身承诺混乱、路径断裂、前置条件消失，那 CI 只能给它发一张很干净的死亡证明。

### 这些传统都对，但不能一起挤进教程主线

现在可以收回来。Manual / man page 让我们尊重事实准确性；HOWTO 让我们尊重现实任务；literate programming 和 notebook 让我们尊重理解顺序；docs-as-code 让我们尊重工程验收。这些传统没有一个是错的。

真正的问题是：**它们解决的是不同读者动作。** 查事实、做任务、理解背景、学习入门、验证材料，这些动作都重要，但不能同时挤进 tutorial 的主线位置。否则文章会变成一种很有现代工程气息的混合怪：既像 reference，又像 HOWTO，又像架构文章，又像 CI checklist，唯独不像教程。

所以 Diátaxis 的价值就出现了。它不是为了发明四个漂亮目录名，而是为了把长期混用的读者动作重新拆开。只有先拆开，我们才知道哪些内容该留在 tutorial 里，哪些该挪出去，哪些可以链接，哪些应该延后。

这就是技术考古的意义：不是怀旧，而是看清混乱并非偶然。它是几条正确传统在同一个页面里抢方向盘的结果。


### 从这些传统里拿什么，不拿什么

技术考古如果只停在“原来以前有这些东西”，那还是资料搬运。真正有用的是把每条传统能给 tutorial 的东西和不能给 tutorial 的东西拆开。

| 传统 | 能给 tutorial 的东西 | 不能直接搬进 tutorial 的东西 |
|---|---|---|
| Manual / man page | 准确性、版本边界、参数事实、可查证结构 | 参数大全式完整性、按对象而不是按学习路径组织材料 |
| HOWTO | 任务边界、步骤顺序、验证动作、故障恢复 | 把完成一次任务误当成获得可复用理解 |
| Literate programming / notebook | 按人的理解顺序组织代码与解释，把输出作为叙事材料 | 沉迷解释，把教程写成思辨散文或实验随笔 |
| Docs-as-code | 示例、链接、格式、构建进入工程验收 | 以为 CI 通过就等于读者学会 |

这张表背后的判断很简单：**tutorial 可以借这些传统的工具，但不能继承它们的主承诺。** 它可以向 manual 借准确，向 HOWTO 借步骤，向 notebook 借叙事，向 docs-as-code 借验收；但它自己的主承诺仍然是学习路径。

这也是很多“看起来很现代”的技术文档会翻车的地方。它有版本控制，有 CI，有文档站，有漂亮主题，有搜索，有代码块复制按钮，有 reference，有架构图，有教程目录。单看每个部件都不错，合在一起却仍然让新读者走不通。原因不是工具不够，而是承诺没拆开。

从历史里能学到的，不是“哪一种传统更高级”，而是“每一种传统都有自己的读者动作”。文档写作最怕的不是传统太少，而是拿错传统。拿 manual 的完整性写 tutorial，拿 HOWTO 的任务紧迫感写学习路径，拿 explanation 的概念密度压新手，拿 CI 的绿灯冒充教学验证——这些都不是资料不足，而是坐标错位。

换句话说，技术考古不是为了给文章添文化感，而是为了给后面的四象限找病因。没有这一步，Diátaxis 看起来像一套凭空冒出来的分类法；有了这一步，Diátaxis 才像一把把旧债拆开的刀。

## Diátaxis 四象限：写作坐标系，不是四个筐

Diátaxis 把技术文档拆成 tutorials、how-to guides、reference 和 explanation 四种模式，并强调它们服务于用户的不同需求[@diataxis_overview]。但如果只把这句话背下来，文章还是会写歪。Diátaxis 真正有用的地方，不在四个标签，而在这张两轴交叉的图。

![Diátaxis 四象限原图（本地化副本）](/images/blog/engineering/diataxis.png)

*图 1：Diátaxis 上游四象限图的本地副本，原图来自 Diátaxis 项目页面[@diataxis_overview]；作者 Daniele Procida，项目许可为 CC BY-SA 4.0[@diataxis_license]。Diátaxis compass 页面则给出了用两轴判断文档模式的实际提问方式[@diataxis_compass]。本文未重绘该图，只在本站本地化保存，避免远程热链。*

这张图必须先看两条轴，不要一上来就把它当成四个筐。

纵轴是 **Action / Cognition**：读者此刻主要是在做，还是在理解。Action 不是“有命令”，而是读者目标要通过动作推进；Cognition 不是“没有代码”，而是读者目标主要在建立认识、查证事实或理解关系。

横轴是 **Acquisition / Application**：读者是在获得新能力，还是在应用已有能力。Acquisition 不是“新手专属”，而是读者要把某种知识或技能纳入自己可复用的能力系统；Application 也不是“高手专属”，而是读者已经有基本背景，现在要把它用到某个具体任务或事实查询里。

这两条轴交叉起来，四个象限就不是作者拍脑袋分出来的目录，而是四种读者动作：

| 模式 | Diátaxis 坐标 | 读者此刻的问题 | 文档主承诺 | 最容易写坏的方式 |
|---|---|---|---|---|
| Tutorial | Action + Acquisition | 我第一次怎样学会？ | 带读者走过一条安全、可复现、能产生学习反馈的路径 | 还没成功先讲架构；把参数大全塞进来；分支太早 |
| How-to guides | Action + Application | 我现在怎样完成这个任务？ | 帮已有基本背景的读者把具体任务做成 | 反复讲新手基础；一个页面塞多个任务；异常分支失控 |
| Reference | Cognition + Application | 这个字段、命令、参数到底是什么？ | 提供准确、完整、可扫描、可查证的事实结构 | 写故事、写路线，让查事实的人读长篇叙事 |
| Explanation | Cognition + Acquisition | 为什么这样设计？我该怎样理解？ | 建立心智模型，讲清概念、关系、背景和取舍 | 抢走 tutorial 主线，让读者迟迟看不到反馈 |

一句话版就是：tutorial 带我学会一次；how-to 告诉我这件事怎么做；reference 让我查准事实；explanation 让我理解为什么。

这组区分看起来简单，真正落笔时却很硬。判断一篇文档的主模式，不是看它有没有步骤、有没有解释、有没有表格、有没有代码。Reference 里可以有代码例子，tutorial 里也可以有表格，how-to 里也会解释前置条件，explanation 里也可以放图。关键是：**页面主承诺到底服务哪一种读者动作？**

这也是很多文档 review 会失焦的原因。Reviewer 看到 tutorial 里没有列全参数，就说“不完整”；看到 reference 里缺少连贯案例，就说“不友好”；看到 how-to 没有从基础概念讲起，就说“新手不懂”；看到 explanation 没给步骤，就说“不落地”。这些意见可能都出于好心，但如果不先判断页面主承诺，就会把页面往错误方向拽。

Diátaxis 不是硬分类学。真实页面当然会混合元素。Django first app tutorial 里会解释 URL 和 view，Rust guessing game 里会讲 match、loop 和随机数，Kubernetes 架构文档里也会有事实结构[@django_first_app; @rust_guessing_game; @kubernetes_cluster_architecture]。这不构成反例。

真正的边界是：**局部混合可以接受，主承诺混乱不可以。** Tutorial 里可以有解释，但解释必须服务当前学习路径；reference 里可以有示例，但示例不能把页面变成教程；how-to 里可以提醒概念，但不能把任务页写成入门课；explanation 里可以有事实表，但事实表不能替代概念关系。

如果把 Diátaxis 用成“这里有解释，所以它不是 tutorial”这种洁癖工具，那它也会变成另一种糊弄。好吧，框架本身没有错，被人拿来当锤子砸所有东西，才是真的麻烦。


### 不要用目录名骗自己

这里还要补一个很现实的坑：很多项目的目录名和页面主承诺并不一致。`tutorials/` 目录里可能放着安装 HOWTO，`guides/` 目录里可能混着 tutorial 和 explanation，README 里更是常年住着四类文档的大杂院。判断模式时如果只看 URL 或栏目名，基本等于闭着眼睛给文件贴标签。

更稳的办法是问四个问题：

1. 读者来到这个页面时，最想完成的是学习、做事、查证，还是理解？
2. 如果读者只读完这一页，页面承诺给他的结果是什么？
3. 页面失败时，伤害最大的是路径、任务、事实，还是心智模型？
4. 页面最应该被怎样验收：学习路径测试、任务复现、事实审校，还是概念解释审阅？

这四个问题比目录名更可靠。比如一个标题叫“Getting started”的页面，如果主体是安装命令、环境要求和 CLI smoke test，它可能更像 installation how-to 或 minimal tutorial 的混合；一个标题叫“Guide”的页面，如果主体是字段表和默认值，它实际上就是 reference；一个 README 的 quickstart 如果只负责让读者看到第一段可运行反馈，它可以承担 tutorial 入口，但它通常不等于完整 tutorial。

这也解释了为什么“局部混合可以接受，主承诺混乱不可以”这么重要。真实文档的边界经常是毛的，不是每个页面都能像教科书一样纯净。但只要主承诺清楚，局部元素就能各就各位；一旦主承诺不清，所有元素都会互相打架。

所以 Diátaxis 最好被当成写作前的坐标系，而不是发布后的贴标签游戏。写之前先定承诺，比写完以后再争它到底算哪类，要有用得多。

## Tutorial 的真正任务：带读者获得第一次可重复的理解

现在回到本文主战场。Diátaxis 对 tutorial 的定位很明确：tutorial 是 learning-oriented，它服务的是用户技能和知识的 acquisition / study，而不是直接帮用户完成某个工作任务[@diataxis_tutorials]。这句话落到写作上，会挡住一大堆看起来无害的偷懒做法。

Tutorial 不是“有步骤的文章”。有步骤的不一定是 tutorial。Kubernetes 的 ConfigMap 任务页围绕“如何让 Pod 使用 ConfigMap”展开，主承诺是帮读者完成一个具体任务[@kubernetes_configmap_task]；Django 自定义 management command 页面也不是从“Django 是什么”开始，而是直接围绕如何创建自定义命令展开[@django_custom_commands]。这些页面很有价值，但它们更接近 how-to。

Tutorial 的任务，是设计一条学习路径。读者跟着走，不只是把某个玩具任务跑完，而是获得下一次能独立复现的理解。所谓“第一次成功”，也不是作者炫耀 demo 跑起来了，而是读者能说清：刚才我做了什么，系统给了我什么反馈，这一步连接了哪个概念，下一次我能不能自己再走一遍。

### Minimal tutorial 与 learning-oriented tutorial 都成立

这里必须先拆掉一个误解：tutorial 不等于短文，也不等于十分钟 quickstart。更稳的分法是两档。

第一档是 **minimal tutorial / quickstart 型**。它的目标是尽快形成第一层反馈，比如安装后跑出第一个页面、执行第一个命令、启动第一个服务、看到第一个测试通过。Django first app 的开头部分就是典型例子：创建项目、启动开发服务器、写第一个 view、接上 URL，让读者很快看到“这个系统真的动起来了”[@django_first_app]。

第二档是 **learning-oriented tutorial / 教材型**。它不一定短，甚至可以相当长，但每一段都围绕学习目标推进。Rust Book 的 guessing game tutorial 就是这类：它借一个猜数字小游戏承载变量、输入、依赖、随机数、比较、循环、错误处理等概念[@rust_guessing_game]。React 的 tic-tac-toe tutorial 也类似，用一个小游戏逐步引出组件、props、state 和交互更新[@react_tic_tac_toe]。它们不是因为篇幅长就变成 explanation，也不是因为有项目任务就变成 how-to。

判断标准不是“短不短”，而是路径有没有被设计过。一个很短的页面如果只让读者复制三行命令，却不知道为什么成功，它可能只是薄薄的 HOWTO；一个很长的页面如果每一步都给出反馈、解释和下一步连接，它仍然可以是 tutorial。

所以不要拿“教程要短”当口号。更准确的说法是：**tutorial 要有最小成功闭环，长教程要有连续阶段闭环。** 短教程尽快给读者第一层成功，长教程则必须更勤快地给阶段反馈。篇幅越长，反馈越不能稀薄；否则读者会在一条看起来宏伟的学习路线里越走越虚。

### 第一条成功路径不是业务任务，而是学习反馈

Tutorial 需要让读者看到成功标志，但这个成功标志不能只理解成“某个业务任务完成了”。它至少有两类反馈。

第一类是**即时输出**：服务启动、页面出现、命令返回预期内容、测试通过、日志里出现某个关键字段、图表渲染出来。即时输出解决的是“我是否走在正确路径上”。没有即时输出，读者只能靠信仰继续往下走。工程里最不缺的就是靠信仰运行的东西，文档就别再添乱了。

第二类是**阶段自检**：读者能否解释刚才那一步把哪个概念接了起来，能否判断一个小变化会带来什么影响，能否把刚才的动作抽象成下一次可复现的模式。阶段自检解决的是“我是否真的学到了”。没有阶段自检，读者可能只是把命令抄完了。

这两类反馈缺一不可。只有即时输出，教程容易退化成打字训练；只有阶段自检，教程容易变成纸上谈兵。好 tutorial 要让读者既看到系统反馈，也看到自己的理解在长出来。

好吧，这里可以说得再刻薄一点：如果读者只会把命令复制完，但不知道刚才连接了什么东西，那不是教程成功，是打字员训练成功。

### Tutorial 最怕三位邻居一起抢方向盘

Tutorial 最容易被写坏，是因为它站在“行动 + 学习”的交界处。它需要读者动手，所以容易被 how-to 的任务冲动带跑；它需要读者理解，所以容易被 explanation 的背景冲动带跑；它需要材料准确，所以容易被 reference 的完整性带跑。

Reference 会诱惑作者说：“这个参数以后会用到，不如现在列全。”How-to 会诱惑作者说：“反正读者都动手了，不如顺手教他部署、调优、迁移、接 CI。”Explanation 会诱惑作者说：“既然要学，就先把架构、历史、哲学、权衡都讲清楚。”

这些话听起来都很有道理。坏教程往往就坏在每一句都很有道理。它不是荒唐地错，而是合理地碎。

教程作者必须学会拒绝。不是拒绝资料，不是拒绝任务，不是拒绝解释，而是拒绝它们抢走主线。真正该做的是把这些内容安排到正确位置：必要解释留在当前步骤旁边，参数大全挪到 reference，真实任务挪到 how-to，设计哲学挪到 explanation，教程结尾再给清晰下一步。

Tutorial 的克制不是贫瘠，而是路径纪律。你不是不知道更多东西，你只是知道现在不该全说。


### 三个 tutorial 案例：短、长、项目型，都要看反馈密度

为了避免把 tutorial 讲成抽象口号，还是把几个典型案例拆细一点。

Django first app 的价值，不只是“它有步骤”。它一开始就把读者放进一个很小的闭环：安装环境、创建项目、启动开发服务器、看到页面、写 view、接 URL。每一步都能产生反馈，而且反馈和概念是贴在一起的。读者不是先读完整个 Django 架构，而是在看到第一个响应之后，再逐步知道项目、应用、视图、URLconf 这些东西怎样连起来[@django_first_app]。

Rust guessing game 则说明 tutorial 不必只做 hello world。它用一个小项目承载语言概念：读取输入、引入依赖、生成随机数、比较大小、处理错误、循环执行。它的篇幅更长，但长不是问题，关键是每一段都在推进一个学习目标，并且读者能通过编译、运行、报错和输出获得反馈[@rust_guessing_game]。这种 tutorial 如果写得好，读者不是“完成了一个游戏”，而是第一次摸到 Rust 的若干基本工作方式。

React tic-tac-toe tutorial 又是另一种项目型学习路径。它不是把 React API 全部列出来，而是用一个小游戏逐步组织组件、props、state 和交互更新[@react_tic_tac_toe]。它当然包含解释，但解释依附于正在构建的东西。读者每改一次代码，都能看到 UI 行为变化。这种“动作—反馈—解释”的节奏，正是 learning-oriented tutorial 站得住的地方。

这三个案例放在一起，能拆掉两个误会。第一，tutorial 不是短才好；没有反馈的短文也可能很差。第二，tutorial 不是项目越真实越好；真实任务太多、分支太早，反而会把学习路径拖散。教程里的项目应该像训练场，不像战场。训练场要足够真实，让动作有意义；也要足够可控，让学习能发生。

如果一个教程写到一半，读者已经需要处理真实生产环境权限、网络策略、历史数据迁移、组织流程和性能调优，那它很可能已经越界成多篇 how-to 的集合了。作者此时最该做的不是继续往下写，而是停下来问：第一条学习路径到底在哪里？

### Tutorial 里的解释应该像路标，不该像景点

Tutorial 并不排斥解释。没有解释的教程很容易变成“把这些命令贴进去”。但解释在 tutorial 里的位置应该像路标：帮助读者知道自己在哪里、下一步往哪里走、刚才为什么要转弯。它不该像景点，让读者每走十米就停下来参观一段宏大背景。

一个实用判断是：解释完这一段之后，读者能不能更顺利地完成当前或下一步？如果能，它大概率该留；如果只是作者觉得“这个也很重要”，但对当前路径没有直接帮助，就应该挪到 explanation 或后续阅读。

例如在 Django tutorial 里，解释 URLconf 和 view 的关系是必要的，因为读者马上要修改路由并看到响应；但如果此时展开 Django middleware、ORM 设计、部署模型，就会把学习路径拉爆。Rust guessing game 里解释 `Result` 和错误处理是必要的，因为读者会立刻遇到解析输入失败；但如果顺手展开 Rust 所有权系统全景，第二章可能直接变成半本书。

这就是教程写作里最难的克制：你知道更多，但你要先证明读者此刻需要知道。

## How-to、Reference、Explanation：三位邻居各自怎么写

既然 tutorial 不能把另外三类内容都吞掉，那它们各自应该怎么写？这一节不展开成完整文档写作指南，只把和本文主线相关的边界讲清楚。否则读者刚从 tutorial 的泥潭里爬出来，又被本文拖进另一口大锅，那就很喜剧了。

### How-to guide：任务必须单一，前置条件必须明确

Diátaxis 对 how-to guides 的定位是帮助已有一定背景的用户解决具体问题[@diataxis_howto]。这句话里的关键词是“具体问题”。How-to 的主承诺不是让读者系统学习，而是让读者完成一个现实任务。

一个好 how-to 至少要钉住四件事：任务目标、适用前提、操作步骤、验证与恢复。Google 的 procedures 指南也强调，过程文档应围绕任务步骤、上下文、动作和结果组织[@google_procedures]；Microsoft 关于 step-by-step instructions 的风格指南同样强调步骤要按顺序、清晰、面向用户动作[@microsoft_step_instructions]。

Kubernetes “Configure a Pod to Use a ConfigMap” 是很好的 how-to 样本。它不承担“从零学习 Kubernetes”的责任，而是放在任务语境下说明如何创建 ConfigMap、如何在 Pod 中使用它、如何验证结果[@kubernetes_configmap_task]。Django 自定义 management command 页面也是类似：读者已经在 Django 项目语境里，现在要创建自己的命令[@django_custom_commands]。

How-to 最怕两个问题。第一个是任务发散：标题写“如何配置 X”，正文顺手塞进安装、架构、调优、迁移、排障、最佳实践，最后页面像一棵被风吹乱的树。第二个是读者前提消失：作者默认读者知道集群、权限、目录、账号、版本、上下文，读者跑到一半才发现自己连入口都不在。

How-to 的克制是任务边界。它可以链接 tutorial 给新手补背景，可以链接 reference 查参数，可以链接 explanation 理解设计；但页面自己要守住任务。读者是来办事的，不是来参加作者的知识展览会。

### Reference：像地图，不像导游词

Diátaxis 对 reference 的定位很冷静：reference 是事实性、信息性的文档，面向已经知道自己要查什么的读者[@diataxis_reference]。它的美德不是亲切，而是准确、完整、可扫描、稳定。

Django model field reference 的中心是字段、选项、类型、默认值、约束、版本变化等事实结构[@django_model_field_reference]。Kubernetes Pod API reference 则围绕对象 schema、字段、类型和说明展开[@kubernetes_pod_api_reference]。读者来这里不是为了被带着走一遍，而是为了查“这个字段到底能不能这样写”“这个对象到底有哪些属性”“这个默认值是什么”。

Reference 可以有例子，但例子应服务查证，不应篡位成教学叙事。Reference 可以解释一点上下文，但不能让查事实的人先读三屏故事。Reference 的信息架构比语言温度更重要：标题层级、字段顺序、索引、交叉引用、版本标记、废弃说明、默认值、边界条件，这些才是它的骨架。

把 reference 写成游记，是一种非常隐蔽的折磨。作者可能觉得自己很体贴：“我多讲一点，读者就更容易理解。”读者的真实想法可能是：“我只是想查一个字段，为什么要陪你走完一段人生？”

地图可以有图例，可以有注释，可以有比例尺，但不要写成旅行散文。Reference 的尊严在于让事实可靠地站在那里。

### Explanation：讲为什么，但别抢教程饭碗

Diátaxis 把 explanation 放在帮助读者理解背景、原因、关系和取舍的位置[@diataxis_explanation]。它不是操作指南，也不是事实索引，而是心智模型建设。

Next.js 的 Rendering Philosophy 页面就是 explanation 的例子：它不是教读者按步骤做一个页面，而是在解释渲染模型、框架设计和权衡逻辑[@nextjs_rendering_philosophy]。Kubernetes Cluster Architecture 也类似，它把控制平面、节点、组件关系等系统结构讲清楚，帮助读者理解集群如何组织[@kubernetes_cluster_architecture]。

Explanation 的问题不在于它不重要，而在于它太容易显得重要。作者写 tutorial 时，一旦觉得“读者不理解这个设计就不行”，就会忍不住把 explanation 整段塞进去。然后读者还没完成第一条成功路径，先被“为什么”淹没。

这并不是说 tutorial 里不能讲为什么。恰恰相反，完全不解释的 tutorial 很容易变成咒语。但 explanation 在 tutorial 里必须短、准、贴着当前步骤。它应该回答“为什么此刻需要知道这个”，而不是“关于这个概念我还能讲多少”。

Explanation 自己独立成文时，则可以放开讲：历史背景、设计权衡、替代方案、失败案例、概念关系、系统边界。它的读者不是急着完成当前任务的人，而是想建立更深理解的人。读者动作不同，文章呼吸方式就不同。

### 四类文档不是等级，而是分工

到这里可以把四类文档再压缩成一个判断：它们不是等级关系，而是分工关系。

Tutorial 不比 how-to 高级，reference 不比 explanation 低级。一个成熟项目需要它们互相配合：tutorial 让人进门，how-to 让人办事，reference 让人查证，explanation 让人理解。缺任何一块，读者都会在某个时刻被迫拿错工具。

最糟糕的文档体系，不是没有四个目录名，而是所有页面都试图同时做四件事。每篇都像 tutorial，每篇又像 reference，每篇都塞一点 philosophy，每篇都顺手解决几个任务。结果是读者找不到真正该看的东西，作者也不知道自己到底在维护什么。

这就是 Diátaxis 的实际价值：不是让目录看起来更专业，而是让读者动作少打架。


### 同一技术语境下的四态对照

如果还嫌抽象，可以拿 Kubernetes 这一类大型项目做一个粗对照。同一个生态里，读者动作会非常明显地分开：

| 读者动作 | 更合适的文档 | 为什么 |
|---|---|---|
| 第一次学习 Kubernetes 基础 | Kubernetes Basics 这类 tutorial | 读者需要通过受控路径理解对象、部署、扩缩容等基本动作 |
| 把 ConfigMap 接进 Pod | ConfigMap task / how-to | 读者已经在 Kubernetes 语境里，要完成一个具体配置任务 |
| 查 Pod 字段 | Pod API reference | 读者要事实、字段、类型、默认值和 schema，不要叙事 |
| 理解集群如何组织 | Cluster Architecture explanation | 读者要控制平面、节点、组件关系和系统心智模型 |

这不是说 Kubernetes 文档每一页都完美，也不是说它所有页面都能被 Diátaxis 纯净分类。这里要看的，是大型项目为什么必须让文档承担不同职责。新手学习、任务操作、事实查证、架构理解，混成一页就会互相污染。

反过来，如果一个小项目暂时没有精力维护四套完整目录，也不代表它不能借这套思路。哪怕只有 README 和几篇文档，也可以在 README 里明确分区：先给最小学习路径，再给常见任务入口，再给 API/reference 链接，再给设计解释。结构不一定大，承诺要清楚。

这就是“分工”二字的实际含义。不是为了文档站仪式感，而是为了让读者不用在每个页面重新猜作者到底想干什么。

## 好 tutorial 的内部结构：从学习目标倒推

如果把 tutorial 当学习路径，而不是当资料合集，它的结构就能倒推出来。

The Good Docs Project 的 tutorial template 把学习目标、目标读者、前置背景、before you begin、steps、summary、next steps 等部分列出来[@gooddocs_tutorial_template]。这说明好 tutorial 并不是靠作者现场发挥玄学，它确实有一套可以检查的骨架。

但骨架不是模板崇拜。模板只能提醒你该问什么，不能替你判断取舍。真正难的是：哪些解释现在必须讲，哪些解释应该推迟；哪些任务可以进入第一条路径，哪些应该挪到后续 how-to；哪个输出是读者能看懂的成功标志，哪个输出只是作者自己看着舒服。

下面这张表，是笔者更愿意在教程 PR 里看到的结构检查：

| 部件 | 它解决的问题 | 写作时要问 | 失败信号 |
|---|---|---|---|
| 学习目标 | 读者最终会获得什么能力 | 目标能否用一句话说清？ | 只写“本文介绍 X”，没有说读者能做什么、理解什么 |
| 目标读者 | 谁适合读，谁不适合读 | 读者能否判断自己该不该继续？ | 新手和熟手被塞进同一路径，互相折磨 |
| 前置条件 | 环境、账号、权限、版本、依赖 | 读者第一步失败时能否排查？ | 跑到一半才发现缺权限、缺账号、版本不对 |
| 非目标 | 本文主动不讲什么 | 哪些重要内容应该延后？ | 一篇教程背完整个宇宙 |
| 路径步骤 | 按学习顺序组织动作 | 每一步是否只推进当前学习目标？ | 过早分支、跳步、解释过量、任务发散 |
| 即时输出 | 告诉读者材料没坏 | 读者能否看到可观测反馈？ | 命令执行完不知道算不算成功 |
| 阶段自检 | 告诉读者理解在长出来 | 读者能否解释这一步建立了什么？ | 复制完命令但完全不知道意义 |
| 失败恢复 | 给高频失败方式留出口 | 偏离 happy path 后去哪查？ | 一报错就掉进井里 |
| 下一步 | 把读者导向后续文档 | 学完后该读 how-to、reference 还是 explanation？ | 教程结束后读者仍然站在门口发呆 |

这个结构里最容易被忽略的是“非目标”。很多作者不敢写不讲什么，仿佛承认边界就是不专业。其实恰恰相反，边界是专业性的表现。你知道自己此刻不该讲什么，才说明你真的在保护学习路径。

第二个容易被忽略的是“阶段自检”。即时输出比较容易想到：页面有没有出来，命令有没有成功，测试有没有过。阶段自检则麻烦一些，因为它要求作者站在读者脑子里想：读者此刻应该形成哪一个小理解？比如 Django first app 里，看到开发服务器启动只是即时输出；理解 URLconf 如何把路径连到 view，才是阶段自检的一部分[@django_first_app]。

第三个容易被忽略的是“下一步”。Tutorial 不该在结尾突然撒手。读者走完第一条路径后，最自然的问题是：我下一步该做真实任务，查 API，还是理解架构？这时教程应该把他引到 how-to、reference 或 explanation，而不是留下一个“恭喜你完成了本教程”的空礼花。

教程写作说到底是一种路径设计。路径设计不等于把路修得很长，而是让每个岔路口都有理由，每个反馈点都可见，每个出口都知道通向哪里。


### 从坏教程改起：先删支线，再补反馈

如果手上已经有一篇混乱 tutorial，笔者不建议一上来润色句子。句子再顺，路径断了还是断。更实用的改法可以分四步。

第一步，划出第一条成功路径。把读者从打开页面到获得第一次可重复理解的路径用一条线标出来。只要不在这条线上，先标成支线。注意，这一步不要急着删除内容，只是先承认主线在哪里。

第二步，给每个步骤补反馈。每一步完成后，读者应该看到什么？如果失败，最可能是什么原因？如果成功，他应该理解哪个小概念？没有反馈的步骤，要么补即时输出，要么补阶段自检，要么考虑删掉。

第三步，把支线迁出去。参数表、完整配置、生产部署、性能调优、设计哲学、历史背景、异常分支，不是不要，而是放到 reference、how-to 或 explanation。Tutorial 可以链接它们，但不让它们占据当前路径。

第四步，重写开头和结尾。开头必须告诉读者本文会带他学会什么、不讲什么、需要什么前置条件；结尾必须告诉读者下一步去哪，而不是一句“恭喜完成”。

这四步听起来像编辑工作，实际上是工程重构。你在重构的不是文字，而是读者的状态机：入口、状态、转移、反馈、异常恢复、出口。如果读者状态机没有设计，文章再漂亮也只是页面级装饰。

### 哪些内容应该延后，而不是删除

很多作者抗拒“教程不要讲太多”，是因为误以为这等于删掉自己辛苦整理的资料。其实更准确的说法是：不要让这些资料堵住第一条路径。

可以延后的内容包括：完整参数表、所有异常分支、生产部署方案、架构全景、性能对比、历史设计争论、替代方案大全、复杂安全配置、多平台差异、组织流程细节。它们很重要，但重要不等于必须现在讲。

一个好办法是在 tutorial 里设置“下一步”或者“延伸阅读”出口：

- 想把这个 demo 接到真实项目？去 how-to。
- 想查所有配置项？去 reference。
- 想理解为什么这样设计？去 explanation。
- 想处理常见错误？去 troubleshooting / how-to。

这样做的效果不是减少信息，而是让信息在正确时刻出现。读者不是不知道更多资料存在，而是不必在第一条路径上被这些资料拦住。

## 复杂工具怎么办：拆体系，不要堆长文

复杂工具当然不可能靠一篇 tutorial 讲完。越复杂的系统，越需要把不同读者动作拆开，而不是把所有东西塞进“从入门到精通”这种巨大标题下面。

一个比较稳的文档体系，大概会长成这样：

```text
Tutorials/
  - 最小成功闭环
  - 第一个真实项目
  - 进阶学习路径
How-to guides/
  - 如何接入 CI
  - 如何迁移旧项目
  - 如何处理常见错误
Reference/
  - CLI 参数
  - 配置文件 schema
  - API / SDK reference
Explanation/
  - 架构设计
  - 核心概念
  - 取舍与边界
```

这不是为了让目录看起来漂亮，而是为了让读者动作少打架。学习时走 tutorial，做任务时看 how-to，查事实时看 reference，想理解设计时读 explanation。每类文档都可以互相链接，但不要互相冒充。

现实当然不会这么干净。很多项目不是从零开始规划文档站，而是已经有一大坨历史文档：README 里有安装、quickstart、API 表、设计哲学、FAQ、贡献指南；文档站里有“入门教程”其实是参数手册；issue 里还有散落的解决方案；博客文章里讲了真正的设计背景。想一次性重构全站，基本等于给自己找一个永远不会开始的理由。

更务实的做法是渐进重构。

第一步，给现有页面标主承诺。不要先改标题，不要先调目录，先问：这个页面主要服务 Action 还是 Cognition？服务 Acquisition 还是 Application？它的读者是来学习、做事、查证，还是理解？如果一个页面答不出来，说明它已经开始混。

第二步，找最伤读者的断点。通常最该先修的不是“目录名不优雅”，而是第一条学习路径断了。新读者第一次进来跑不通，后面 reference 再漂亮也很难挽回信任。读者对项目的第一层信任，是非常脆的。

第三步，把内容迁到合适位置。参数表、字段表、选项说明挪到 reference；真实任务和运维动作挪到 how-to；架构、历史、设计权衡挪到 explanation；tutorial 只保留当前学习路径必须使用的材料，并把其他内容作为下一步链接。

第四步，补交叉链接。拆开不是割裂。Tutorial 里应该在恰当位置链接 reference，让读者知道以后去哪里查；how-to 里可以链接 explanation，解释为什么某个任务需要这样做；reference 里可以链接 tutorial，告诉新手如果还没入门先去哪里。

这套方法听起来朴素，但比“我们重写一份完整文档站”靠谱得多。后者经常停在宏大计划里，前者至少能先救一个真实读者路径。


### README 不是垃圾场，README 是交通枢纽

复杂项目还有一个高发问题：README 被迫承载一切。项目定位、安装、quickstart、API 摘要、性能 benchmark、FAQ、贡献指南、引用格式、路线图、论文链接、联系方式，全都住在一个页面里。久而久之，README 就变成项目门口的杂物间。

README 当然重要。很多读者第一次接触项目就是从 README 开始。但 README 更适合做交通枢纽，而不是完整城市。它可以承担四个入口：一句话说明项目解决什么问题；一个极短 quickstart 让读者看到第一层反馈；几个常见任务链接；稳定 reference / explanation 入口。它不该把所有内容都压缩进自己肚子里。

这点对开源库尤其重要。一个库的 README 如果没有任何可运行反馈，读者可能不知道项目是否值得试；如果 README 塞满 API 细节，读者又找不到第一步。最稳的做法是：README 先让人相信“这东西能解决我的问题，并且我能快速看到它动起来”，然后把更重的材料导向专门页面。

换句话说，README 不是文档体系的替代品，而是文档体系的路口。路口的价值在于指向清楚，不在于把所有道路都修在路口上。

复杂系统当然可以有复杂结构，但不能把不同目的的文字混成一锅。那不是降低门槛，是把门槛拆碎了铺在地上，读者每走一步都要扎脚。

## 工程验收：机器验证材料，真人验证路径

Tutorial 写完以后，不能只靠作者自己读一遍说“挺顺”。尤其是技术教程，它一边承诺学习路径，一边包含命令、代码、版本、链接、输出、截图、环境假设。这里任何一块坏掉，读者都会把成本付出去。

所以教程验收至少需要两条腿：机器验证材料，真人验证路径。

### 机器验收：先别把低级问题交给读者

机器验收关注的是：教程里的材料是否仍然真实可用。

示例代码和命令能不能运行？输出片段是不是来自真实工具行为？链接和交叉引用是否还有效？版本敏感内容有没有写明版本或日期？示例里有没有真实 token、密码、私钥、内部域名？Google 的 code samples 指南强调示例要清晰、可复制、避免读者踩不必要的坑[@google_code_samples]；timeless documentation 则提醒作者少写会快速过期的“现在 / 当前 / 最新”之类表达[@google_timeless_documentation]。

机器验收可以包括很多层次：

- 文档构建：Markdown / MDX / Sphinx / Astro 等构建必须通过。
- 示例测试：doctest、rustdoc tests、notebook 执行、脚本化 smoke test。
- 链接检查：外链、内链、交叉引用、图片路径。
- 格式与术语：Markdown lint、Vale、术语表、标题层级。
- 安全护栏：示例中禁止真实凭据，危险命令必须有上下文， destructive 操作不能伪装成普通步骤。
- 时效检查：版本号、日期、依赖范围、弃用提示。

Sphinx doctest、Rustdoc documentation tests、GitLab documentation testing 都是这条线上的例子[@sphinx_doctest; @rustdoc_documentation_tests; @gitlab_documentation_testing]。它们证明不了教程好，但能防止教程坏得太低级。

这里必须说句不太客气的话：如果教程里的命令从来没有跑过，输出靠作者想象，链接靠读者自己修，那它不是“文档还需要完善”，它是把 QA 成本外包给读者。读者不是你的免费测试环境。

### 静态质量护栏不是可执行文档，但也不能省

有些检查不属于严格意义上的“可执行文档”，但依然是工程验收的一部分。比如链接检查、术语检查、格式检查、图片路径检查、敏感信息扫描、命令行示例格式检查。这些机制不会告诉你学习路径好不好，但可以把一批低级错误挡在发布前。

这类护栏的价值在于降低噪声。一个教程如果到处是断链、错别字、格式崩坏、引用错乱，读者会在还没接触核心内容之前就开始怀疑项目质量。文档当然不可能永远不出错，但如果错误能被机器发现，却被留给读者发现，那就是维护流程的问题。

不过也不要把 lint 当成文档质量本身。格式全绿不代表文章能教会人。很多糟糕文档都可以通过 lint，它们就像衣服熨得很平整的稻草人，看起来像个人，走近发现里面是空的。

### 真人任务测试：学习路径到底有没有断

机器能证明材料没坏，但不能证明读者知道下一步该干什么。Tutorial 至少需要一次“目标读者按教程独立走关键路径”的验证。

NN/g 对 usability testing 的描述很朴素：让参与者执行任务，研究者观察他们的行为和反馈[@nng_usability_testing]；任务场景还需要给参与者一个真实可理解的目标，而不是抽象命令[@nng_task_scenarios]。放到 tutorial 上，就是找目标读者按教程独立走一遍，观察他在哪一步停顿、哪句话误解、失败后有没有恢复路径、结束后是否知道下一步去哪。

一个轻量任务测试可以这样做：

1. 找一个接近目标读者的人，不要找已经熟悉该系统的维护者。
2. 给他教程入口和任务目标，不额外口头解释。
3. 观察他独立执行：哪里停顿、哪里回读、哪里复制失败、哪里误解概念。
4. 记录卡点，而不是现场替他补课。
5. 测试后问三个问题：你认为自己完成了什么？哪一步最不确定？下一步你会去哪查？
6. 把卡点回填到教程：补前置条件、补反馈、删支线、改措辞、补恢复路径。

这不是大型用户研究，也不需要把一篇博客教程搞成论文实验。但至少一次真人任务测试，能发现很多作者自己永远看不见的问题。作者对自己写的路径太熟了，熟到会自动跨过坑；新读者不会。

这里的盖章句可以很硬：**CI 证明材料没坏，真人任务测试证明路径没断。少任何一条，教程都只能算“看起来能用”。**


### 机器验收和真人测试不要互相冒充

这里特别容易出现两种偷懒。

第一种偷懒是“我们有 CI，所以教程没问题”。这话只能证明材料层面的风险被压了一部分。CI 可以跑命令、测代码、查链接、扫格式，但 CI 不知道读者有没有在第一个概念处迷路。CI 也不知道某句话在作者看来很自然，在新读者那里会不会被理解成另一个意思。

第二种偷懒是“我们找人读过，所以不用自动化”。这也不对。真人任务测试能发现路径问题，但真人不应该替你发现所有断链、错别字、不可执行示例和格式错误。把机器能发现的问题交给人肉测试，是另一种浪费。

所以更合理的顺序是：先用机器把材料层面的低级问题清掉，再用真人验证路径层面的理解问题。机器验收在前，是为了不让用户测试变成环境排障；真人测试在后，是为了不让 CI 绿灯冒充教学成功。

如果一定要用一句工程话概括：机器验收是单元测试和静态检查，真人任务测试更像端到端体验验证。单元测试过了不代表产品好用；端到端测了一次也不代表每个函数都可靠。两者本来就不是互相替代的东西。

### 版本与时效：不要让“最新”变成过期炸弹

教程还有一个很烦但必须处理的问题：时效性。技术教程一旦涉及版本、命令、截图、UI、云平台、依赖安装，就会开始老化。老化不可怕，可怕的是作者假装它不会老化。

Google 的 timeless documentation 建议避免依赖“当前”“最新”“最近”这类会随时间漂移的说法[@google_timeless_documentation]。放到博客教程里，就是尽量写清楚版本、日期、访问时间和验证环境。比如“本文写作时使用 Django 6.0 文档页面作为案例”比“最新 Django 文档”稳得多；“treevalue v1.5.0 installation 页面”比“treevalue 安装文档”更可复核。

这不是学术洁癖，而是对读者负责。读者看到明确版本，就知道差异来自哪里；读者看到“latest”，只能猜作者到底指哪一天的 latest。把时间漂移藏起来，等于把未来维护成本藏到读者身上。

教程验收里也应该包含时效检查：版本敏感内容是否写明版本，外部页面是否需要访问日期，截图是否可能过期，命令是否依赖当前默认值。别等读者复制失败之后才想起“哦对，官方上周改了”。

## Checklist 与反模式：教程 PR 到底该审什么

如果把上面这些话落到 PR review，笔者建议至少使用下面这份阻断级 checklist。它不是装饰，是挡住烂教程的门槛。

### A. 模式与目标

- [ ] 这篇文档的主模式已经明确：tutorial / how-to / reference / explanation。
- [ ] 如果它是 tutorial，学习目标能用一句话说清。
- [ ] 它没有把 reference、explanation 或多个 how-to 任务塞进 tutorial 主线。
- [ ] 它正面承认局部混合的现实，但页面主承诺没有混乱。

### B. 路径与反馈

- [ ] 读者能在教程中完成一个最小成功闭环。
- [ ] 每个关键阶段都有可观测成功标志，并区分即时输出与阶段自检。
- [ ] 失败后读者知道当前可能错在哪里，以及下一步查什么。
- [ ] 教程结尾给出明确下一步：继续 tutorial、进入 how-to、查 reference，或读 explanation。

### C. 示例与材料

- [ ] 关键命令 / 代码 / 输出来自真实运行，或明确标注不能自动运行。
- [ ] 示例使用安全假数据或保留域名，不硬编码真实 token、密码、私钥。
- [ ] 版本敏感内容写明版本号或日期，不靠 `latest`、`current`、`now` 这类词撑场面。
- [ ] 外链、内链、图片、引用和交叉引用已经通过自动检查或人工复核。

### D. 验收与维护

- [ ] 文档构建、链接、交叉引用和基础 lint 通过。
- [ ] 可执行示例进入 doctest / 文档测试 / 等价 CI，或明确说明人工验证方式。
- [ ] 至少一次由目标读者按教程独立走过关键路径，且卡点被记录和处理。
- [ ] 后续维护入口明确：谁更新版本、谁修示例、谁处理读者反馈。

这份 checklist 的价值在于，它逼你问一个不那么体面的问题：这篇教程到底是带读者学会了，还是只是把作者知道的东西摊出来了？

反模式也可以集中收束成一组，避免在文章里到处重复：

1. **参数大全冒充教程**：读者还没开始，先收到一张字段表。
2. **架构论文开局**：第一条反馈还没出现，概念图已经砸下来。
3. **没有最小成功闭环**：读者不知道何时算成功。
4. **命令和输出靠想象**：作者没跑过，读者先踩雷。
5. **解释过量**：每个概念都重要，于是主线被支线淹没。
6. **环境前提消失**：版本、账号、依赖、权限全靠读者猜。
7. **没有失败恢复**：一旦偏离 happy path，读者只能去搜索引擎捞自己。
8. **PR review 只看格式**：错别字都修了，路径还是断的。

其中最毒的一条大概是最后一条。错别字都修了，读者还是走不通。这种 review 看起来很认真，实际上全在给事故擦边框。

如果要把 C/I/M 审查也套进来，笔者会这么分：学习路径断裂、事实错误、命令不可复现、引用无来源、编造作者经历，这些是 Critical；主承诺不清、案例分类混乱、验收缺失、重要边界没讲，是 Important；标题不够锋利、个别段落太绕、局部表达不顺，是 Minor。工程洁癖最多到 M，除非它真的影响事实、学习路径或验收可靠性。


### 一段教程 PR review 应该长什么样

为了让 checklist 不停留在纸面上，可以想象一个 tutorial PR 的 review 口径。

不太好的 review 是这样的：

> “整体写得不错，建议补充更多背景；第 3 行有错别字；代码块缩进调整一下。”

这些意见不是完全没用，但它们没有碰到教程的主承诺。更像样的 review 应该问：

> “这篇教程承诺让读者完成第一个可重复闭环，但第 2 步和第 3 步之间缺少可观测反馈；读者不知道服务是否启动成功。建议补一个明确输出或截图，并说明如果端口被占用应该怎么恢复。”

或者：

> “这里把完整配置表塞进 tutorial 主线，导致第一次成功反馈被推迟到第 6 屏。建议只保留当前路径用到的两个配置项，完整表迁到 reference，并在段末给链接。”

再或者：

> “这段架构解释本身没错，但它服务的是 explanation，不服务当前步骤。建议压缩成两句路标，把完整设计权衡挪到后续 explanation。”

这类 review 的共同点是：它不只评价文字，而是评价读者路径。它能指出哪里断、为什么断、怎样修。这样的 review 才配得上“教程验收”四个字。

如果 review 只会修格式、补背景、加链接，却不问目标读者能不能独立走通，那它看起来很勤奋，实际是在给坏路径贴瓷砖。瓷砖贴得再整齐，路断了还是断了。

## 拿自己的旧材料试刀：treevalue 与 Issue / Milestone

外部案例讲多了，文章很容易变成资料综述。这里还是拿自己的旧材料试一刀。

先说明边界：下面不是要倒过来证明“当年早就按 Diátaxis 设计过”。没有。更准确的说法是：今天站在新的文档思维框架下，回头看公开旧材料，看看它们天然承担了哪些不同文档职责。能复盘就复盘，不能编造的地方不编造。

### treevalue：不是当年有意设计，而是今天回头看职责分化

treevalue 是一个处理嵌套数据结构的 Python 库，旧文《treevalue——Master Nested Data Like Tensor》更像项目价值、设计意图和能力展示的介绍文章[@hansbug_treevalue_old_blog]。仓库 README 则承担项目概览、安装、quick usage、性能、贡献和 citation 等入口职责[@treevalue_repository]。v1.5.0 文档里的 installation 页面主要解决安装和命令行初验问题[@treevalue_installation_150]。

这些材料如果用 Diátaxis 回头看，会自然分出几种职责：

| 材料 | 更接近的模式 | 它在读者路径里的作用 |
|---|---|---|
| README quick usage | minimal tutorial / 入口说明的混合 | 让读者快速看到库怎么用，建立第一层兴趣和反馈 |
| Installation 页面 | installation how-to / minimal tutorial 边界 | 帮读者把环境装起来，并看到基础命令能运行 |
| API 文档 | reference | 查具体对象、函数、参数和行为 |
| 旧文介绍 | explanation / project narrative | 解释为什么这个库值得存在、它解决什么抽象问题 |

这里最有意思的不是“treevalue 文档当年多么标准”。恰恰相反，当初搞 treevalue 时并没有系统考虑 tutorial / how-to / reference / explanation 这些问题。真正有意思的是：一个真实开源项目天然会长出不同读者动作。有人第一次跑起来，有人查 API，有人想理解为什么要把嵌套数据做成 tensor-like 的样子，有人只想知道这个库值不值得接进自己的项目。

如果仅按公开材料和本文框架重新组织 treevalue 的入门材料，更清楚的拆法会是：README 保留项目定位和极短 quickstart；tutorial 做一个从普通 nested dict 到可操作 tree value 的小闭环；how-to 放常见任务，比如怎样映射、过滤、接入真实数据结构；reference 保持 API 查证；explanation 再讲它为什么借用了 tensor-like 的思路，以及这种抽象在什么场景下站得住。

这样拆不是为了显得目录高级，而是为了避免把新手拖进信息泥潭。一个第一次接触 treevalue 的读者，不应该在“安装”“快速例子”“API 细节”“设计哲学”“性能对比”之间来回跳。读者的第一条路径越清楚，他越有机会走到后面的 reference 和 explanation。

换句话说，treevalue 这个案例在本文里不是自夸材料，而是提醒自己：当年没有明确说出的文档职责，今天可以重新看清。技术项目会长大，文档思维也得补课。

### Issue / Milestone 使用指导：更像给团队成员的 how-to

再看旧文《关于 Issue/Milestone 的使用指导》[@hansbug_issue_milestone_old_blog]。这篇旧文如果今天重看，笔者更愿意把它放在 how-to guide 的位置：它不是给完全空白的新手上一门“GitHub 协作导论”，也不是列出所有字段含义的 reference，而是给已经进入课程或团队协作现场的人一套操作路径。

也就是说，它要解决的问题是：在一个多人协作场景里，怎样使用 issue、milestone、任务拆分和进度跟踪，才不至于把团队协作搞成一锅粥。读者并不是来系统学习项目管理理论，也不是来查 GitHub 每个按钮的官方定义；读者是要把眼前协作跑起来。

这就解释了为什么判断一篇文档之前，必须先判断它承诺解决什么问题。如果把这篇旧文当 tutorial，会嫌它没有从零建立 GitHub 协作心智模型；如果当 reference，会嫌它不够完整；放回 how-to 的位置，才知道应该问什么：任务场景是否清楚？步骤是否能执行？协作边界是否说清？常见滥用是否被挡住？团队成员看完能不能减少误解和无效沟通？

这也是自家案例的意义。框架不是拿来给外部文档贴标签玩，而是拿回来重新审视自己的旧材料。只有敢拿自己的材料试刀，才知道刀锋到底切不切得开问题。

### 本站写作系统：不是所有模板都叫 tutorial

顺手再补一个辅助边界。本站现在有 BibTeX / CSL 引用约定、`{{PAGE_URL}}` quick-start 模板、AGENTS 维护规则等材料。这些东西里有步骤、有模板、有代码块，但它们不自动变成 tutorial。

例如 citation 约定更接近 reference + how-to：它告诉作者可用语法、文件放哪里、哪些写法会构建失败。`{{PAGE_URL}}` quick-start 模板则更像 agent-consumable how-to：它给出一段可复制指令，帮助读者把当前页面交给本地 agent 处理。它们都很有用，但它们的主承诺不是“带一个新手第一次学会技术写作系统”。

这个例子小，但能帮我们挡住一个常见误判：**有步骤、有模板、有可复制代码块，不等于 tutorial。** 还是那句话，看主承诺，看读者动作，不看表面元素。

## 总结：别把资料密度误认为教学质量

最后收一下。

Tutorial 不是 reference。Reference 的尊严在准确，tutorial 的尊严在路径。How-to 的尊严在把任务做成，explanation 的尊严在把为什么讲透。四类文档谁也不比谁高级，但谁也不该冒充谁。

写 tutorial 最容易犯的错，就是把作者的不安全感转嫁给读者：我怕你不知道，所以我全写上；我怕你以后要查，所以我全塞进来；我怕你误解，所以我先讲半天背景。结果读者还没获得第一次成功反馈，先被作者的焦虑压垮了。

真正好的 tutorial 要反过来：少一点炫耀资料密度，多一点路径纪律；少一点“我知道很多”，多一点“你现在应该看到什么”；少一点万能长文，多一点可复现的第一步。

技术教程不是文案活。它是读者进入一个系统的第一条工程路径。路径坏了，后面的 API reference 再漂亮、架构解释再深刻、CI badge 再绿，也救不回读者第一次被摔出去的体验。

说到底，文档也是工程资产。工程资产不是堆在那里显得很多，而是关键时刻真的能用。教程尤其如此——它不是把知识摆在读者面前，而是把读者带到能自己继续走的地方。

别把这事想得太轻。一个走不通的 tutorial，伤的不是一页文档的面子，而是读者对整个项目的第一层信任。
